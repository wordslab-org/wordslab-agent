# Weaviate API Analysis — Vector Database, Hybrid Search, RAG & Agentic AI

> **Base URL:** `http://[YOUR-WEAVIATE-HOST]:8080/v1` (REST) | **gRPC port:** `50051` (local) / `443` (Weaviate Cloud)
> **Docs:** `https://docs.weaviate.io/weaviate` | **Product:** `https://weaviate.io` | **Auth:** API key / OIDC tokens
> **SDKs:** `weaviate-client` (Python v4, TypeScript v3, Java, Go, C#) | **Query Agent:** `weaviate-agents` (Python)
> **Description:** Weaviate is an open-source, AI-native vector database that stores both data objects and their vector embeddings. It offers semantic vector search, BM25 keyword search, hybrid search (fusing vector + keyword), generative search (RAG), reranking, aggregations, multi-tenancy, vector quantization, and a built-in Query Agent that translates natural language into database operations. It is modular — vectorization, generation, and reranking are delegated to pluggable model provider integrations (OpenAI, Cohere, Google, Anthropic, Hugging Face, Ollama, Jina, NVIDIA, Mistral, and more).

## 1. Platform Overview & Core Concepts

### Main Concepts

Weaviate's architecture is organized around these core abstractions:

- **Collection** — A named group of data objects that share a schema definition. Each collection has its own vector space, vectorizer, index configuration, and optional generative/reranker model integrations. Identified by name (must start with an uppercase letter).
- **Data Object** — A JSON document belonging to a collection. Has one or more `properties` and (typically) a `vector` embedding. Identified by a UUID.
- **Property** — A named, typed field on a data object (e.g. `title: TEXT`, `points: INT`). Supports per-property tokenization, vectorization, and indexing settings.
- **Vector** — An array of floats representing the semantic embedding of an object. Can be auto-generated by a vectorizer module or user-provided.
- **Named Vectors** — Multiple vector spaces per collection, each with its own vectorizer, index, and compression. Enables multi-model search on the same data.
- **Cross-Reference** — A directional link between objects (potentially across collections), similar to a foreign key. Does not affect vectors.
- **Shard** — A self-contained storage unit within an index. Each shard contains an object store, an inverted index store, and a vector index. Shards distribute load across nodes.
- **Module** — A pluggable integration for vectorization, generation, reranking, or backups. The Weaviate core is model-agnostic; modules provide model connectivity.

### Search Pipeline

```
1. Retrieval (required)
   ├── Filter: Narrow results by criteria (pre-filtering)
   └── Search: Find most relevant entries
         ├── Keyword (BM25) — token frequency ranking
         ├── Vector — semantic similarity
         └── Hybrid — fuses keyword + vector
2. Rerank (optional)
   └── Reorder results with a cross-encoder model
3. Generative (optional, RAG)
   └── Send results + prompt to a generative LLM
```

### End-to-End Flows

**Basic search pipeline:**
```
Create collection (vectorizer + properties) ──▶ Insert objects (auto-vectorized) ──▶ Search (vector/keyword/hybrid)
                                                                                                    │
                                                                      (optional) Rerank ──▶ (optional) Generative RAG ──▶ response
```

**Query Agent pipeline:**
```
Natural language query ──▶ QueryAgent.ask() / .search()
                               │
                   ┌───────────┴────────────┐
                   │ LLM analyzes query      │
                   │ Rewrites into Weaviate   │
                   │ queries + filters       │
                   └───────────┬────────────┘
                               │
              ┌────────────────┼────────────────┐
              ▼                ▼                 ▼
        Vector search    Keyword search     Aggregation
              └────────────────┼────────────────┘
                               │
                    Combine results ──▶ LLM generates final answer (Ask mode)
                                     ──▶ Return raw objects (Search mode)
```

### Key Differentiators

- **Open-source & self-hostable** — Full control via Docker, Kubernetes, or Weaviate Cloud. Data stays in your environment (VPC option).
- **Modular model integration** — 20+ embedding/generative/reranker providers via pluggable modules. Switch models with one line of code.
- **Hybrid search by design** — BM25 + vector fusion with tunable alpha and two fusion algorithms, built into the database (not bolted on).
- **Pre-filtering** — Filters applied before vector search using inverted index + HNSW, with ACORN algorithm for efficient filtered search without brute-force fallback.
- **Multi-tenancy** — Native per-tenant sharding supporting 50,000+ active shards per node (~1M tenants with ~20 nodes).
- **Vector quantization** — Four compression techniques (PQ, BQ, SQ, RQ) with training-free options (RQ) achieving 32x compression at 98-99% recall.
- **Built-in Query Agent** — LLM-powered natural language → database operations, with Ask mode (answer) and Search mode (raw objects).
- **Multiple index types** — HNSW (default), Flat, Dynamic (auto flat→HNSW), HFresh (disk-backed, memory-efficient).
- **gRPC support** — High-performance binary protocol for search and batch imports, auto-negotiated by modern client libraries.

## 2. API Architecture — REST, GraphQL, gRPC

### Main Concepts

Weaviate exposes three complementary APIs, each optimized for different use cases. Modern client libraries (Python v4+, TypeScript v3+) automatically use gRPC for search/query operations when available, falling back to REST/GraphQL otherwise.

### API Summary

| API | Protocol | Port | Primary Use | Key Operations |
|---|---|---|---|---|
| **RESTful API** | HTTP/JSON | 8080 | Instance management & CRUD | Collections CRUD, object CRUD, node status, backups, cluster health, batch import |
| **GraphQL API** | HTTP/JSON (POST to `/v1/graphql`) | 8080 | Search & exploration | `Get` (search), `Aggregate` (aggregations), `Explore` (cross-collection), filters, `nearText`/`nearVector`/`bm25`/`hybrid` |
| **gRPC API** | HTTP/2 + Protocol Buffers | 50051 (local) / 443 (cloud) | High-performance search & batch | Search queries, batch data imports — faster serialization, lower latency |

### GraphQL Query Structure

```graphql
{
  <Function> {
    <Collection> {
      <property>
      _<underscore-property>
    }
  }
}
```

**Example:**
```graphql
{
  Get {
    JeopardyQuestion(
      limit: 2
      nearText: { concepts: ["animals in movies"] }
    ) {
      question
      answer
      _additional { distance }
    }
  }
}
```

### Client Library Connection (Python v4)

```python
import weaviate
from weaviate.classes.init import Auth

client = weaviate.connect_to_weaviate_cloud(
    cluster_url=os.environ.get("WEAVIATE_URL"),
    auth_credentials=Auth.api_key(os.environ.get("WEAVIATE_API_KEY")),
    headers={"X-OPENAI-API-KEY": os.environ.get("OPENAI_API_KEY")},
)
```

### gRPC Protobuf Definitions

The gRPC interface is defined through Protocol Buffer files in the Weaviate source:

| File | Purpose |
|---|---|
| `weaviate.proto` | Core service definitions |
| `batch.proto` | Batch import operations |
| `search_get.proto` | Search query operations |
| `base.proto` | Base/common message types |

### Consistency Levels (Replicated Collections)

GraphQL `Get` queries support tunable read consistency:

| Level | Description |
|---|---|
| `ALL` | Read from all replicas — strongest consistency, highest latency |
| `QUORUM` (default) | Read from majority — balanced |
| `ONE` | Read from any replica — lowest latency, weakest consistency |

```python
from weaviate.classes.config import ConsistencyLevel

questions = client.collections.use("MyCollection").with_consistency_level(
    consistency_level=ConsistencyLevel.QUORUM
)
```

### Analysis

The three-API design separates concerns: REST for management (CRUD, schema, backups), GraphQL for expressive queries (search, aggregation, cross-references), and gRPC for performance-critical paths (search, batch import). The client libraries' auto-negotiation means developers typically don't need to choose — they use idiomatic SDK methods and the library picks the optimal protocol. The GraphQL integer limitation (`int32` only, no `int64`) is a known constraint; the workaround is to use `string` for large integer properties.

## 3. Collections — Schema & Configuration

### Main Concepts

- **Collection = Schema** — A collection defines the class, properties, vectorizer, index config, generative model, and reranker for all objects within it. Weaviate requires a schema before adding data, but auto-generates one if omitted.
- **Auto-schema** — If no schema is provided, Weaviate infers property types from incoming data and creates the collection automatically.
- **Vector Config** — Configures how vectors are created (vectorizer module) and how they are indexed (index type, distance metric, quantization).
- **Named Vectors** — Multiple vector spaces per collection, each with independent vectorizer, index, and compression settings.

### Collection Creation

```python
from weaviate.classes.config import Configure, Property, DataType, Tokenization, VectorDistances

client.collections.create(
    "Article",
    vector_config=Configure.Vectors.text2vec_openai(
        vector_index_config=Configure.VectorIndex.hnsw(
            ef_construction=300,
            distance_metric=VectorDistances.COSINE,
        ),
    ),
    generative_config=Configure.Generative.openai(model="gpt-4o"),
    reranker_config=Configure.Reranker.cohere(),
    properties=[
        Property(
            name="title",
            data_type=DataType.TEXT,
            vectorize_property_name=True,
            tokenization=Tokenization.LOWERCASE,
            description="The title of the article.",
        ),
        Property(
            name="body",
            data_type=DataType.TEXT,
            skip_vectorization=True,
            tokenization=Tokenization.WHITESPACE,
        ),
    ],
)
```

### `client.collections.create()` Parameters

| Parameter | Type | Required | Default | Description |
|---|---|---|---|---|
| `name` | string | yes | — | Collection name (must start uppercase) |
| `properties` | list[Property] | no | auto-schema | Property definitions |
| `vector_config` | VectorConfig / list[VectorConfig] | no | — | Vectorizer + index configuration |
| `generative_config` | GenerativeConfig | no | — | Generative model for RAG |
| `reranker_config` | RerankerConfig | no | — | Reranker model |
| `multi_tenancy_config` | MultiTenancyConfig | no | disabled | Multi-tenancy settings |
| `replication_config` | ReplicationConfig | no | factor=1 | Replication settings |

### Named Vectors (Multiple Vector Spaces)

```python
client.collections.create(
    "ArticleNV",
    vector_config=[
        Configure.Vectors.text2vec_cohere(
            name="title",
            source_properties=["title"],
            vector_index_config=Configure.VectorIndex.hnsw(),
        ),
        Configure.Vectors.text2vec_openai(
            name="title_country",
            source_properties=["title", "country"],
            vector_index_config=Configure.VectorIndex.hnsw(),
        ),
        Configure.Vectors.self_provided(
            name="custom_vector",
            vector_index_config=Configure.VectorIndex.hnsw(),
        ),
    ],
    properties=[
        Property(name="title", data_type=DataType.TEXT),
        Property(name="country", data_type=DataType.TEXT),
    ],
)
```

### Multi-Vector Embeddings (ColBERT / ColPali, v1.30+)

```python
client.collections.create(
    "DemoCollection",
    vector_config=[
        Configure.MultiVectors.text2vec_jinaai(
            name="jina_colbert",
            source_properties=["text"],
        ),
        Configure.MultiVectors.self_provided(name="custom_multi_vector"),
    ],
    properties=[Property(name="text", data_type=DataType.TEXT)],
)
```

### Collection Management Operations

| Operation | SDK Method | Description |
|---|---|---|
| Check existence | `client.collections.exists("Article")` | Returns boolean |
| Get definition | `collection.config.get()` | Read full collection definition |
| List all | `client.collections.list_all(simple=False)` | List all collection definitions |
| Update | `collection.config.update(...)` | Update description, properties, index params, models |
| Delete | `client.collections.delete("Article")` | Delete collection + all objects |
| Delete all | `client.collections.delete_all()` | Remove all collections |
| Add property | `collection.config.add_property(Property(...))` | Add a new property to existing collection |
| Add named vector | `collection.config.add_vector(vector_config=...)` | Add a new named vector (v1.31+) |

### Vectorizer Configuration Options

| Method | Description |
|---|---|
| `Configure.Vectors.text2vec_openai()` | OpenAI embeddings |
| `Configure.Vectors.text2vec_cohere()` | Cohere embeddings |
| `Configure.Vectors.text2vec_google()` | Google embeddings |
| `Configure.Vectors.text2vec_huggingface()` | Hugging Face embeddings |
| `Configure.Vectors.text2vec_ollama()` | Ollama (local) embeddings |
| `Configure.Vectors.text2vec_jinaai()` | Jina AI embeddings |
| `Configure.Vectors.text2vec_transformers()` | Self-hosted transformers |
| `Configure.Vectors.self_provided()` | User-provided vectors (no vectorizer) |
| `Configure.MultiVectors.text2vec_jinaai()` | Jina ColBERT multi-vector |
| `Configure.MultiVectors.self_provided()` | User-provided multi-vector |

### Vector Index Types

| Method | Description |
|---|---|
| `Configure.VectorIndex.hnsw(...)` | HNSW graph index (default) — scalable, in-memory |
| `Configure.VectorIndex.flat()` | Flat index — brute-force, memory-efficient, for small datasets |
| `Configure.VectorIndex.dynamic()` | Dynamic index — auto-switches flat→HNSW at 10k objects (experimental, v1.25) |
| `Configure.VectorIndex.hfresh()` | HFresh index — disk-backed, memory-efficient (v1.36) |

### Analysis

Weaviate's collection system is a rich schema layer that decouples storage from model choice. The `Configure.Vectors.*` builder pattern enables declarative configuration of vectorizer, index type, distance metric, quantization, and filter strategy in one call. Named vectors are a standout feature — you can have multiple embedding models on the same objects and query each independently. The ability to add named vectors post-creation (v1.31) without reindexing existing objects prevents accidental large vectorization costs, though it means existing objects must be manually re-inserted to populate the new vector space.

## 4. Data Objects — CRUD Operations

### Main Concepts

- **Object = JSON + Vector** — Each data object is a JSON document with typed properties and an optional vector embedding.
- **UUID** — Every object has a UUID for uniqueness across all collections. Can be auto-generated, user-specified, or deterministically derived from content.
- **Auto-vectorization** — If a vectorizer module is configured on the collection, Weaviate automatically generates vectors from object properties on insert.
- **References** — Cross-references to other objects can be set at insert time.

### Object Creation

```python
jeopardy = client.collections.use("JeopardyQuestion")
uuid = jeopardy.data.insert({
    "question": "This vector DB is OSS & supports automatic property type inference",
    "answer": "Weaviate",
    "points": 500,
})
```

### `collection.data.insert()` Parameters

| Parameter | Type | Required | Default | Description |
|---|---|---|---|---|
| `properties` | dict | yes | — | Object properties as key-value dict |
| `uuid` | string | no | auto-generated | Object UUID |
| `vector` | list[float] or dict[str, list[float]] | no | auto-vectorized | Explicit vector(s); dict for named vectors |
| `references` | dict | no | — | Cross-references, e.g. `{"hasCategory": category_uuid}` |

### Object with Explicit Vector

```python
uuid = jeopardy.data.insert(
    properties={"question": "...", "answer": "Weaviate"},
    vector=[0.12345] * 1536
)
```

### Object with Named Vectors

```python
uuid = reviews.data.insert(
    properties={"title": "A delicious Riesling", "review_body": "...", "country": "Germany"},
    vector={
        "title": [0.12345] * 1536,
        "review_body": [0.31313] * 1536,
        "title_country": [0.05050] * 1536,
    }
)
```

### Object with Cross-References

```python
questions.data.insert(
    properties=properties,
    uuid=obj_uuid,
    references={"hasCategory": category_uuid},
)
```

### Object with Geo-Coordinates

```python
publications.data.insert(
    properties={
        "headquartersGeoLocation": {
            "latitude": 52.3932696,
            "longitude": 4.8374263
        }
    },
)
```

### Deterministic UUIDs

```python
from weaviate.util import generate_uuid5

uuid = jeopardy.data.insert(
    properties=data_object,
    uuid=generate_uuid5(data_object),  # Same data → same UUID

```

| Operation | SDK Method | Description |
|---|---|---|
| By ID | `collection.query.fetch_object_by_id(uuid)` | Get single object by UUID |
| List objects | `collection.query.fetch_objects(limit, offset)` | Paginated list (UUID order) |
| By ID + tenant | `collection.with_tenant(t).query.fetch_object_by_id(uuid)` | Multi-tenant retrieval |

### Object Update & Delete

| Operation | SDK Method | Description |
|---|---|---|
| Update properties | `collection.data.update(uuid=..., properties=...)` | Replace object properties |
| Replace vector | `collection.data.update(uuid=..., vector=...)` | Replace object vector |
| Delete | `collection.data.delete_by_id(uuid)` | Delete single object |
| Delete multiple | `collection.data.delete_many(where=Filter(...))` | Delete by filter |

### Multi-tenancy Object Operations

```python
multi_tenantA = multi_collection.with_tenant("tenantA")
object_id = multi_tenantA.data.insert(properties={"question": "..."})
```

### Analysis

The object CRUD API is straightforward — `collection.data.insert()` for creation, `collection.query.fetch_object_by_id()` for retrieval, and `collection.data.update()` / `delete_by_id()` for mutations. The auto-schema feature (inferring property types from incoming data) reduces friction for prototyping. Deterministic UUIDs via `generate_uuid5` are a valuable pattern for idempotent ingestion (re-inserting the same data doesn't create duplicates). The named-vector dict syntax (`vector={"name": [...]}`) cleanly maps to collection-level named vector definitions. Geo-coordinate objects use a nested `{latitude, longitude}` structure.

Weaviate's property system offers fine-grained control over how each property participates in vectorization and keyword search. The `vectorize_property_name` flag lets you include the field name in the vectorization context (useful when property names are semantically meaningful).

## 6. Vector Index Configuration

### Main Concepts

Weaviate supports four vector index types, each with distinct performance characteristics:

| Index Type | Memory | Build Speed | Search Speed (large) | Best For |
|---|---|---|---|---|
| **HNSW** (default) | High | Moderate | Very fast | Large collections, high QPS |
| **Flat** | Very low | Fast | Slow (linear) | Small datasets, multi-tenancy (per-tenant small data) |
| **Dynamic** (v1.25) | Adaptive | Fast→Moderate | Adaptive | Collections that start small, may grow (auto flat→HNSW at 10k objects) |
| **HFresh** (v1.36) | Low | Moderate | Fast | Memory-constrained deployments, disk-backed, large-scale |

### HNSW Index Parameters

| Parameter | Type | Default | Description |
|---|---|---|---|
| `ef_construction` | int | 128 | Controls build-time search width. Higher = better recall, slower build |
| `max_connections` (M) | int | 32 | Max graph connections per node. Higher = better recall, more memory |
| `ef` | int | -1 (dynamic) | Search-time list size. -1 enables dynamic ef. Higher = better recall, slower search |
| `dynamicEfMin` | int | 5 | Minimum dynamic ef value |
| `dynamicEfMax` | int | 25 | Maximum dynamic ef value |
| `dynamicEfFactor` | int | 10 | Multiplier applied to query limit to compute ef |
| `cleanupIntervalMs` | int | 300000 | Interval for async cleanup of deleted objects |
| `vectorCacheMaxObjects` | int | 1e12 | Max vectors in memory cache |
| `flatSearchCutoff` | int | 40000 | Switch to flat search when filter matches < this % of dataset (~15%) |
| `filterStrategy` | enum | `ACORN` (v1.34+) | Filter algorithm: `ACORN` or `sweeping` |
| `distance_metric` | enum | `COSINE` | Distance function |

### Dynamic ef Formula

```
ef = min(max(dynamicEfMin, queryLimit * dynamicEfFactor), dynamicEfMax)
```

### Distance Metrics (`VectorDistances` enum)

| Metric | Description | Formula |
|---|---|---|
| `COSINE` (default) | Cosine similarity | 1 - cos(a, b) |
| `DOT` | Dot product (inner product) | -dot(a, b) |
| `L2_SQUARED` | Squared Euclidean | sum((a_i - b_i)^2) |
| `HAMMING` | Hamming distance | count of differing dimensions |
| `MANHATTAN` | Manhattan (L1) distance | sum(abs(a_i - b_i)) |

> **Note:** HFresh index only supports `COSINE` and `L2_SQUARED`.

### Filter Strategies

| Strategy | Description | Best For |
|---|---|---|
| `ACORN` (default v1.34+) | Custom implementation inspired by ACORN paper. Preserves graph integrity, skips non-matching nodes during traversal | Restrictive filters with low correlation to query vector — significantly faster for large datasets |
| `sweeping` | Traverses HNSW graph evaluating distance + filter at each node | Legacy; ACORN generally outperforms |

### Flat-Search Cutoff

When a filter matches less than ~15% of the dataset, HNSW traversal becomes exhaustive. Weaviate automatically switches to a flat (brute-force) search on the filtered subset, which is more efficient than traversing the full graph. The cutoff is configurable via `flatSearchCutoff` in `vectorIndexConfig`.

### Analysis

The HNSW index is the workhorse of Weaviate — it offers logarithmic search complexity and supports full CRUD (unlike many HNSW implementations that require rebuilding). The dynamic ef feature is a key usability optimization: instead of manually tuning `ef` for different query limits, the formula automatically scales the search list size proportionally to the requested result count, bounded by min/max values. The ACORN filter strategy (v1.34+) is a significant advancement — it solves the classic "restrictive filter degrades HNSW" problem by maintaining graph connectivity while skipping non-matching nodes, without falling back to brute-force. The flat-search cutoff at ~15% is a complementary optimization for extremely restrictive filters.

## 7. Vector Quantization (Compression)

### Main Concepts

Vector quantization compresses vector embeddings to reduce memory footprint and improve search speed, at the cost of some recall. Weaviate offers four techniques:

| Technique | Compression | Training | Index Support | Added |
|---|---|---|---|---|
| **PQ** (Product Quantization) | ~24x | Yes (codebook) | HNSW only | — |
| **BQ** (Binary Quantization) | 32x | No | HNSW, Flat | — |
| **SQ** (Scalar Quantization) | 4x | Yes (min/max) | HNSW only | — |
| **RQ 8-bit** (Rotational Quantization) | 4x | No | HNSW (v1.32), Flat (v1.35) | v1.32 |
| **RQ 1-bit** (Rotational Quantization) | ~32x | No | HNSW (v1.33), Flat (v1.35) | v1.33 |

### Product Quantization (PQ)

Reduces vector size by: (1) splitting dimensions into segments (subspaces), (2) quantizing each segment independently to 256 centroids (1 byte per segment).

**Example:** 768-dim vector (768 × 4 bytes = 3072 bytes) → 128 × 1 byte = 128 bytes (~24x compression).

| Parameter | Description |
|---|---|
| `segments` | Number of segments. Must divide evenly into vector dimensions. Larger = higher recall, more memory |
| `trainingLimit` | Max objects per shard for training (recommended: 10,000–100,000) |
| `encoder.type` | `kmeans` (default) or `tile` (experimental, faster import, better recall on some datasets) |
| `encoder.distribution` | (tile only) Distribution for centroid generation |

**Distance calculation:** Asymmetric — query vector stays uncompressed, only stored vectors are compressed.

### Binary Quantization (BQ)

Converts each dimension from 32-bit float to 1 bit (sign bit). 32x compression. Lossy — works best with Cohere V3 and OpenAI ada-002 embeddings. No training required.

### Scalar Quantization (SQ)

Converts 32-bit floats to 8-bit integers (256 buckets). 4x compression. More accurate than BQ. Training analyzes data to determine min/max per dimension, then distributes values uniformly into 256 buckets. Default training set: 100,000 objects per shard.

### Rotational Quantization (RQ)

**Training-free** — can be enabled at index creation with no data analysis.

**8-bit RQ:**
1. Fast pseudorandom rotation (Walsh Hadamard Transform, ~7-10μs for 1536-dim vector)
2. Scalar quantization of rotated vector to 8-bit (min/max per vector)
- 4x compression, 98-99% recall

**1-bit RQ:**
1. Same rotation (padded to ≥256 bits for low-dimensional data)
2. Asymmetric quantization (more precision for query vectors)
- ~32x compression, serves as a more robust alternative to BQ

### Re-scoring (`rescoreLimit`)

When using compressed vectors, Weaviate over-fetches candidates and re-scores them using original uncompressed vectors:

```
fetch_count = max(query_limit, rescoreLimit)
→ compute distances on compressed vectors
→ fetch top fetch_count
→ re-score with original vectors
→ return top query_limit
```

With RQ's high native recall (98-99%), you can often **disable rescoring** (`rescoreLimit=0`) for maximum performance.

### Default Quantization (v1.33)

Set `DEFAULT_QUANTIZATION` environment variable to apply a default quantization to all new collections. Once set on a collection, quantization **cannot be disabled**.

### Analysis

The quantization landscape in Weaviate is mature. RQ (Rotational Quantization) is the standout — being training-free means it can be enabled at collection creation time without a data analysis pass, yet achieves 98-99% recall at 4x compression (8-bit) or ~32x compression (1-bit). The asymmetric distance calculation (query vector stays at full precision) is a key technique for maintaining recall with compressed stored vectors. The re-scoring mechanism with `rescoreLimit` provides a tunable precision-speed tradeoff: set it high for maximum recall, or to 0 with RQ for maximum speed. PQ remains the highest compression option (~24x) but requires training and is HNSW-only.

## 8. Vector Similarity Search

### Main Concepts

Vector search finds objects whose embeddings are closest to a query vector, using a configured distance metric. Weaviate supports four input modalities for vector search:

| Method | Input | Requirement |
|---|---|---|
| `near_text` | Natural language text | Configured vectorizer module |
| `near_vector` | Explicit vector (list of floats) | None |
| `near_object` | Existing object UUID | Object exists in collection |
| `near_image` | Base64-encoded image | Configured multi-modal vectorizer |

### `near_text` — Search with Text

```python
from weaviate.classes.query import MetadataQuery

jeopardy = client.collections.use("JeopardyQuestion")
response = jeopardy.query.near_text(
    query="animals in movies",
    limit=2,
    return_metadata=MetadataQuery(distance=True),

for o in response.objects:
    print(o.properties)
    print(o.metadata.distance)
```

### `near_text` Parameters

|---|---|---|---|
| `query` | string | — | Search text (vectorized by configured module) |
| `limit` | int | — | Max results |
| `offset` | int | — | Pagination offset |
| `distance` | float | — | Max accepted distance (similarity threshold) |

| `target_vector` | string | — | Named vector to search (required if multiple named vectors) |

| `return_properties` | list[str] | all | Properties to return |

### `near_vector` — Search with a Vector

```python
response = jeopardy.query.near_vector(
```

```python
response = jeopardy.query.near_object(
```


### Similarity Thresholds

| Parameter | Description |
|---|---|
| `distance` | Max accepted distance — objects farther than this are excluded |
| `certainty` | Alternative for cosine — 0.0 to 1.0, higher = more similar |
| `auto_limit` (autocut) | Limit to N groups of similar distance — detects natural "drops" in distance |


### MMR Diversity Selection (v1.37 preview)

Maximal Marginal Relevance reranks results for diversity:

```python

    limit=20,          # candidate set

    ),
)
```

| MMR Parameter | Type | Description |
|---|---|---|
| `limit` | int | Results after MMR. Must be ≤ query's top-level `limit` |
| `balance` | float | Relevance-diversity tradeoff (0.0–1.0). 0.5 = balanced |

### Analysis

The four `near_*` methods cover all vector search input modalities — text (most common, uses vectorizer), explicit vector (for custom embeddings), existing object (find similar), and image (multi-modal). The `distance`/`certainty` threshold parameters serve the same purpose (similarity cutoff) with different units — `distance` is the raw metric value (lower = more similar), `certainty` is normalized to 0-1 (higher = more similar, cosine only). The `auto_limit` (autocut) feature is unique — it detects natural "breaks" in the distance distribution to return only the top group(s) without specifying an arbitrary limit. MMR diversity (v1.37 preview) addresses the "all results are variations of the same thing" problem by balancing relevance with result diversity.

## 9. Keyword Search (BM25)

### Main Concepts

- **BM25/BM25F** — Ranking algorithm based on term frequency and inverse document frequency. BM25F extends this to weighted multi-field search.
- **Tokenization** — Configurable per-property (WORD, LOWERCASE, WHITESPACE, FIELD, TRIGRAM).
- **Property Boosting** — Weight specific properties higher with `prop^weight` syntax.
- **Search Operators** — `and` (all tokens required) / `or` (at least N tokens required, v1.31).

### `collection.query.bm25()` — Python

```python
jeopardy = client.collections.use("JeopardyQuestion")
response = jeopardy.query.bm25(
    query="food",
    query_properties=["question^2", "answer"],  # boost question x2
    limit=3,
    return_metadata=MetadataQuery(score=True),
)
```

### `bm25()` Parameters

| Parameter | Type | Default | Description |
|---|---|---|---|
| `query` | string | — | Search string |
| `query_properties` | list[str] | all searchable | Properties to search, with optional `^weight` boost |
| `operator` | BM25Operator | `or` | Search operator: `and_()` or `or_(minimum_match=N)` |
| `limit` | int | — | Max results |
| `offset` | int | — | Pagination offset |
| `auto_limit` | int | — | Autocut |
| `filters` | Filter | — | Pre-search filter |
| `return_properties` | list[str] | all | Properties to return |
| `return_metadata` | MetadataQuery | — | Metadata (score, explain_score) |
| `group_by` | GroupBy | — | Group results |
| `boost` | — | — | Soft ranking (v1.38 preview) |

### BM25 Search Operators (v1.31)

```python

```

### Tokenization Configuration

```python

        Property(name="title", data_type=DataType.TEXT, tokenization=Tokenization.LOWERCASE),

    ],
)
```

### GraphQL Syntax

```graphql
{
  Get {
    JeopardyQuestion(
      limit: 3
      bm25: {
        query: "food"

      question
      answer

    }
  }
}
```

### Analysis

Weaviate's BM25 implementation is full-featured — it supports BM25F (multi-field weighted scoring), configurable tokenization per property (including TRIGRAM for fuzzy/typo-tolerant search), per-property boost weights via the `^weight` syntax, and `and`/`or` search operators with `minimum_match` thresholds (v1.31). The `score` and `explain_score` metadata return the BM25F score and a human-readable explanation of how it was computed. The accent folding (v1.37 preview) and configurable stopword presets (v1.37 preview) are newer additions that improve multilingual and domain-specific search. Compared to OpenAI's file search (which uses internal keyword matching with no exposed tuning), Weaviate's BM25 is highly configurable and transparent.

## 10. Hybrid Search

### Main Concepts

Hybrid search runs vector search and keyword (BM25F) search in parallel, then fuses their results. It combines semantic similarity with exact keyword matching, making it the recommended default search type.

### How Hybrid Search Works

1. **Vector search** — Computes semantic similarity between query embedding and stored vectors
2. **Keyword search** — Computes BM25F scores based on token frequency
3. **Fusion** — Combines results using a fusion algorithm, weighted by `alpha`

### `collection.query.hybrid()` — Python

```python
from weaviate.classes.query import MetadataQuery, HybridFusion

jeopardy = client.collections.use("JeopardyQuestion")
response = jeopardy.query.hybrid(
    query="food",
    alpha=0.25,                                          # 0=keyword, 1=vector
    fusion_type=HybridFusion.RELATIVE_SCORE,
    query_properties=["question^2", "answer"],
    limit=3,
    return_metadata=MetadataQuery(score=True, explain_score=True),
)
```

### `hybrid()` Parameters

| Parameter | Type | Default | Description |
|---|---|---|---|
| `query` | string | — | Query string (used for BOTH keyword + vector by default) |
| `alpha` | float | 0.25 | Weight: 0 = pure keyword, 1 = pure vector, 0.5 = balanced |
| `fusion_type` | HybridFusion | `RELATIVE_SCORE` | Fusion algorithm: `RELATIVE_SCORE` or `RANKED` |
| `vector` | list[float] / HybridVector | — | Explicit query vector (instead of vectorizing `query`) |
| `max_vector_distance` | float | — | Max distance threshold for vector component only |
| `query_properties` | list[str] | all searchable | Properties for keyword search, with `^weight` boost |
| `bm25_operator` | BM25Operator | `or` | BM25 search operator (`and_()` / `or_(minimum_match=N)`) |
| `target_vector` | string | — | Named vector to search (required if multiple named vectors) |
| `limit` | int | — | Max results |
| `offset` | int | — | Pagination offset |
| `auto_limit` | int | — | Autocut (requires `RELATIVE_SCORE` fusion) |
| `filters` | Filter | — | Pre-search filter |
| `return_properties` | list[str] | all | Properties to return |
| `return_metadata` | MetadataQuery | — | Metadata (score, explain_score, distance) |
| `group_by` | GroupBy | — | Group results |
| `boost` | — | — | Soft ranking (v1.38 preview) |

### Fusion Strategies

| Strategy | Default Since | How It Works |
|---|---|---|
| `relativeScoreFusion` | v1.24 | Normalizes scores from each search to 0-1 (max=1, min=0), then weighted sum. Retains more information from original scores. |
| `rankedFusion` | v1.23 and lower | Scores based on rank position: `1/(RANK + 60)`. Only retains ranking, not score magnitude. |

**Ranked fusion formula:** `score = 1/(RANK + 60)`

**Relative score fusion:** `normalized = (score - min) / (max - min)`

### Alpha Parameter

| Alpha | Behavior |
|---|---|
| `0` | Pure keyword search (BM25 only) |
| `0 < alpha < 0.5` | Keyword-dominant |
| `0.5` | Equal weight |
| `0.5 < alpha < 1` | Vector-dominant |
| `1` | Pure vector search |

### HybridVector — Explicit Vector with Move Parameters

```python
from weaviate.classes.query import HybridVector, Move

response = jeopardy.query.hybrid(
    query="California",           # used for keyword search
    vector=HybridVector.near_text(  # used for vector search
        query="large animal",
        move_away=Move(force=0.5, concepts=["mammal", "terrestrial"]),
    ),
    max_vector_distance=0.4,
    alpha=0.75,
    limit=5,
)
```

### Search Thresholds

- `max_vector_distance` — Only applies to the **vector component** of hybrid search. Objects with vector distance > threshold are excluded regardless of keyword score.
- No equivalent threshold for BM25 component or final combined scores (BM25 scores are not normalized/bounded).

### GraphQL Syntax

```graphql
{
  Get {
    JeopardyQuestion(
      limit: 3
      hybrid: {
        query: "food"
        properties: ["question^2", "answer"]
        alpha: 0.25
        fusionType: relativeScoreFusion
      }
    ) {
      question
      answer
      _additional { score explainScore }
    }
  }
}
```

### Named Vectors in Hybrid Search

```python
response = reviews.query.hybrid(
    query="A French Riesling",
    target_vector="title_country",
    limit=3,
)
```

> Named vector collections support hybrid search, but only for **one vector at a time**.

### Analysis

Hybrid search is Weaviate's signature capability — it's a first-class database operation, not a bolted-on feature. The `alpha` parameter provides a smooth continuum from pure keyword to pure vector search, with `relativeScoreFusion` (default) preserving score magnitude information that `rankedFusion` discards. The ability to provide an explicit `vector` parameter (via `HybridVector`) decouples the keyword query from the vector query — you can use different text for each, or even use `move_to`/`move_away` for the vector component while the keyword component uses the raw query string. The `max_vector_distance` threshold applies asymmetrically (vector only, not BM25) because BM25 scores aren't normalized — this is a deliberate design choice documented in the concepts page. The `explain_score` metadata is valuable for debugging hybrid search behavior — it shows exactly how the fused score was computed from the vector and keyword components.

## 11. Filtering

### Main Concepts

- **Pre-filtering** — Filters are applied **before** vector search. Weaviate's inverted index + HNSW combination enables efficient pre-filtering without brute-force search.
- **ACORN Algorithm** (v1.34+) — Default filter strategy that speeds up filtered HNSW searches, especially when filters have low correlation with the query vector.
- **Filter Objects** — Python SDK uses a fluent builder pattern (`Filter.by_property("x").equal("y")`). GraphQL uses a nested `where` clause.

### Python Filter Builder

```python
from weaviate.classes.query import Filter

# Single condition
filters = Filter.by_property("round").equal("Double Jeopardy!")

# Multiple conditions (AND via &)
filters = (
    Filter.by_property("round").equal("Double Jeopardy!") &
    Filter.by_property("points").less_than(600) &
    Filter.not_(Filter.by_property("answer").equal("Yucatan"))
)

# Multiple conditions (OR via |)
filters = (
    Filter.by_property("points").greater_than(700) |
    Filter.by_property("points").less_than(300)
)

# all_of (AND list)
filters = Filter.all_of([
    Filter.by_property("points").greater_than(300),
    Filter.by_property("points").less_than(700),
])

# any_of (OR list)
filters = Filter.any_of([
    Filter.by_property("points").greater_or_equal(700),
    Filter.by_property("points").less_than(500),
])
```

### Filter Methods

| Method | Description |
|---|---|
| `Filter.by_property(name, length=False)` | Filter by a property. `length=True` enables length-based filtering |
| `Filter.by_id()` | Filter by object UUID |
| `Filter.by_ref(link_on=...)` | Filter by cross-reference (chain with `.by_property(...)`) |
| `Filter.by_ref_count(link_on=...)` | Filter by count of references |
| `Filter.by_creation_time()` | Filter by object creation timestamp |
| `Filter.all_of([filters])` | Combine filters with AND |
| `Filter.any_of([filters])` | Combine filters with OR |
| `Filter.not_(filter)` | Negate a filter |

### Comparison Operators

| Method | GraphQL Operator | Description |
|---|---|---|
| `.equal(value)` | `Equal` | Equals |
| `.not_equal(value)` | `NotEqual` | Not equals |
| `.less_than(value)` | `LessThan` | Less than |
| `.less_or_equal(value)` | `LessThanEqual` | Less than or equal |
| `.greater_than(value)` | `GreaterThan` | Greater than |
| `.greater_or_equal(value)` | `GreaterThanEqual` | Greater than or equal |
| `.like(pattern)` | `Like` | Partial match with `*` (zero+) and `?` (one) wildcards |
| `.contains_any(list)` | `ContainsAny` | Property contains any of the values |
| `.contains_all(list)` | `ContainsAll` | Property contains all of the values |
| `.contains_none(list)` | `ContainsNone` | Property contains none of the values |
| `.is_none(bool)` | `IsNull` | Null state check (requires `index_null_state=True`) |
| `.within_geo_range(coordinate, distance)` | `WithinGeoRange` | Geo range filter (distance in meters) |

### GraphQL Filter Syntax

```graphql
{
  Get {
    JeopardyQuestion(
      limit: 3
      where: {
        path: ["round"]
        operator: Equal
        valueText: "Double Jeopardy!"
      }
    ) { question answer }
  }
}
```

### Value Types in GraphQL

| `valueType` | For Data Type |
|---|---|
| `valueInt` | `int` |
| `valueBoolean` | `boolean` |
| `valueText` | `text`, `uuid`, `geoCoordinates`, `phoneNumber` |
| `valueNumber` | `number` |
| `valueDate` | `date` (RFC 3339 timestamp) |
| `valueString` | `string` (deprecated) |

### Geo-Coordinate Filtering

```python
from weaviate.classes.query import Filter, GeoCoordinate

response = publications.query.fetch_objects(
    filters=Filter.by_property("headquartersGeoLocation").within_geo_range(
        coordinate=GeoCoordinate(latitude=52.39, longitude=4.84),
        distance=1000,  # meters
    )
)
```

> **Limitation:** Geo-coordinate filtering is limited to the nearest 800 results from the source location.

### Date Filtering

```python
from datetime import datetime, timezone

filter_time = datetime(2022, 6, 10, tzinfo=timezone.utc)
response = collection.query.fetch_objects(
    filters=Filter.by_property("some_date").greater_than(filter_time),
    limit=3,
)
```

### Cross-Reference Filtering

```python
response = jeopardy.query.fetch_objects(
    filters=Filter.by_ref(link_on="hasCategory").by_property("title").like("*Sport*"),
    return_references=QueryReference(link_on="hasCategory", return_properties=["title"]),
    limit=3,
)
```

### Nested Object Property Filtering (v1.38+ preview)

```python
# Any car has make = "Toyota"
filters = Filter.by_property("cars.make").equal("Toyota")

# First car has make = "Toyota" (index-based)
filters = Filter.by_property("cars[0].make").equal("Toyota")

# Same-element correlation: SAME car is Toyota AND red
filters = (
    Filter.by_property("cars.make").equal("Toyota") &
    Filter.by_property("cars.color").equal("red")
)
```

### Performance Notes

- **`Like` filters** iterate over the entire inverted index — search time scales linearly with dataset size
- **Geo filters** limited to nearest 800 results
- **`indexRangeFilters`** — opt-in range index for `int`/`number`/`date` properties that improves range query performance
- **`indexFilterable`** — roaring bitmap index for match-based filtering (enabled by default)
- **`indexNullState`** — opt-in index for `is_none()` null-state filtering
- **`indexPropertyLength`** — opt-in index for length-based filtering

### Analysis

Weaviate's filter system is comprehensive — it covers equality, comparison, set membership (`contains_any`/`contains_all`/`contains_none`), pattern matching (`like` with wildcards), geo-range, null-state, length, cross-references, reference counts, creation time, and nested object properties (v1.38 preview). The pre-filtering approach (via inverted index + HNSW with ACORN) is a key architectural differentiator — unlike post-filtering systems that discard results after vector search (losing recall), Weaviate's pre-filtering maintains recall even with restrictive filters. The `Filter.all_of()` / `Filter.any_of()` list-style combinators are cleaner than deeply nested `&`/`|` chains for multi-condition filters. The `like` filter performance caveat (linear scan over inverted index) is important to document — for high-cardinality pattern matching, consider `TRIGRAM` tokenization instead.

## 12. Reranking

### Main Concepts

- **Two-Stage Search** — First retrieve with a fast method (vector/keyword/hybrid), then rerank with a more expensive cross-encoder model on the smaller result set.
- **Cross-Encoder Models** — Reranker modules (Cohere Rerank, Hugging Face, Voyage AI) provide more nuanced text understanding than bi-encoder embeddings.
- **Property-Based** — You can rerank based on a specific property of the objects, not just the query.

### `collection.query.*` with `rerank` — Python

```python
from weaviate.classes.query import Rerank, MetadataQuery

response = jeopardy.query.near_text(
    query="flying",
    limit=10,
    rerank=Rerank(
        prop="question",
        query="publication",
    ),
    return_metadata=MetadataQuery(score=True),
)
```

### `Rerank` Parameters

| Parameter | Type | Description |
|---|---|---|
| `prop` | string | Object property to pass to the reranker |
| `query` | string | Query string for the reranker model |
| `model` | string | Which reranker model to use (when multiple configured) |

### Reranker Compatibility

Reranking works with **all search types**:
- Vector search (`near_text`, `near_vector`, `near_object`, `near_image`)
- Keyword search (`bm25`)
- Hybrid search (`hybrid`)

### GraphQL Syntax

```graphql
{
  Get {
    JeopardyQuestion(
      nearText: { concepts: "flying" }
      limit: 10
    ) {
      answer
      question
      _additional {
        distance
        rerank(
          property: "answer"
          query: "floating"
        ) {
          score
        }
      }
    }
  }
}
```

### Response Access

| Context | Python Accessor | GraphQL Path |
|---|---|---|
| Vector search | `o.metadata.score` | `_additional.rerank[].score` |
| BM25 search | `o.metadata.rerank_score` | `_additional.rerank[].score` |

### Reranker Model Configuration

```python
# At collection creation
client.collections.create(
    "Article",
    vector_config=Configure.Vectors.text2vec_openai(),
    reranker_config=Configure.Reranker.cohere(),
)

# Update existing collection
collection.config.update(reranker_config=Reconfigure.Reranker.cohere())
```

### Analysis

Reranking is a clean two-stage pattern: retrieve `limit` objects with a fast search, then rerank them with a cross-encoder model on a specific property. The `prop` parameter is key — it lets you rerank based on a different property than the one used for initial retrieval, enabling more nuanced relevance scoring. The ability to use a different `query` for reranking than for initial retrieval (e.g., retrieve with "flying" but rerank with "floating") supports sophisticated search strategies. The rerank score replaces the original score in metadata, while the original distance/score is preserved separately for debugging. Rerankers are compatible with all search types, making them universally applicable as a search quality enhancement layer.

## 13. Generative Search — RAG

### Main Concepts

- **Generative Search = Search + LLM** — Weaviate performs the search, then passes results + a prompt to a configured generative AI model. Also called "generative search" or "RAG."
- **Two Generation Modes:**
  - **Single Prompt** — Generate a response for **each** retrieved object independently (per-object)
  - **Grouped Task** — Generate **one** response using all retrieved objects together (per-group)
- **Model Integration** — Generative models (OpenAI, Cohere, Google, Anthropic, Ollama, etc.) are configured at the collection level and can be overridden at query time.
- **Prompt Interpolation** — Use `{property_name}` to inject object properties into prompts.

### Single Prompt (Per-Object Generation)


### Analysis

Weaviate's generative search is tightly integrated — the `generate.*` methods are full search methods that accept all search parameters (query, filters, limit, etc.) plus generation parameters (single_prompt, grouped_task). The `single_prompt` vs `grouped_task` distinction is fundamental: single_prompt is for per-object transformation (e.g., "translate this", "summarize this"), while grouped_task is for cross-object reasoning (e.g., "what do these have in common?"). The `{property_name}` interpolation in prompts is powerful — it lets you reference any object property in the prompt, even properties not returned in the search results. The `generative_provider` parameter at query time enables model A/B testing without schema changes. The multimodal support (images in grouped tasks, v1.30+) enables vision-based RAG where the LLM considers images alongside text.

```graphql

```

### Analysis

The aggregation API is well-structured — it mirrors the search API (over_all, near_text, hybrid) but returns computed metrics instead of objects. The `Metrics` class provides typed builders for each data type (text for frequency counts, integer/number for statistics, boolean for true/false counts, date for temporal ranges). The `object_limit` parameter in search-based aggregations controls how many objects are considered for the aggregation (analogous to `limit` in search). The `GroupByAggregate` (distinct from search-level `GroupBy`) enables grouping objects by a property and computing per-group metrics. The `groupBy` limitation (only works with `near<Media>` operators, limited to one property/cross-reference, no nested paths) is worth noting for complex aggregation queries.

## 15. Grouped Search

### Main Concepts

Grouped search organizes search results into groups based on a property or cross-reference, returning multiple objects per group.

### `GroupBy` Parameter

```python
from weaviate.classes.query import GroupBy, MetadataQuery

group_by = GroupBy(
    prop="round",
    objects_per_group=2,
    number_of_groups=2,
)

response = jeopardy.query.near_text(
    query="animals in movies",
    limit=10,
    return_metadata=MetadataQuery(distance=True),
    group_by=group_by,
)

for grp_name, grp_content in response.groups.items():
    print(grp_content.name, grp_content.number_of_objects)
```

### `GroupBy` Parameters

| Parameter | Type | Description |
|---|---|---|
| `prop` | string | Property or reference path to group by |
| `objects_per_group` | int | Max objects per group |
| `number_of_groups` | int | Max number of groups |

### Applicability

`group_by` is available on all search methods:
- `fetch_objects`
- `near_text`, `near_vector`, `near_object`, `near_image`
- `bm25`
- `hybrid`

### Analysis

Grouped search is a presentation-level feature — it groups ranked results by a property (e.g., "show me results grouped by category, 3 per category, max 5 categories"). The `objects_per_group` and `number_of_groups` parameters control the cardinality of the output. This is distinct from `GroupByAggregate` (which computes metrics per group) and from RAG `grouped_task` (which generates text per group). The response format changes from `response.objects` (flat list) to `response.groups` (dict of group name → group content).

## 16. Multi-tenancy

### Main Concepts

- **Per-Tenant Sharding** — Each tenant gets its own shard, providing complete data isolation.
- **Lightweight Shards** — Supports 50,000+ active shards per node (~1M tenants with ~20 nodes).

|---|---|---|---|

| `OFFLOADED` | No | On cloud storage (S3), no access | Yes |

- Length: 4-64 characters

### Analysis

Multi-tenancy in Weaviate is a first-class feature — per-tenant sharding provides data isolation at the storage level, not just at the query filter level. The auto-tenant creation feature (v1.26+) eliminates the need to pre-provision tenants. The tenant lifecycle (`ACTIVE` → `INACTIVE` → `OFFLOADED`) enables cost management — inactive tenants free resources, offloaded tenants move to cheap S3 storage. The `with_tenant()` pattern is clean — it returns a tenant-scoped collection handle that supports all standard operations. The note about backups only including active tenants is important for operational planning.

## 17. Query Agent — Agentic AI

### Main Concepts

The **Query Agent** is a Weaviate Cloud-only pre-built agentic service that uses an LLM to translate natural language questions into Weaviate database operations (searches, aggregations, filters, sorts). It can perform multiple searches across multiple collections in a single call.

- **Weaviate Cloud only** — Not available for self-hosted deployments.
- **Two modes:** Ask (natural language answer) and Search (raw objects).
- **Streaming support** — Real-time response streaming with progress updates.
- **Async support** — Full async/await support for Python.
- **Free tier:** 250 ask queries or 1,000 search queries per month.

### Modes

| Mode | Method | Returns | Best For |
|---|---|---|---|
| **Ask** | `qa.ask()` | Natural language answer + search details | End-user-facing chat, written responses |
| **Search** | `qa.search()` | Raw matching Weaviate objects | Internal search, dashboards, retrieval in pipelines |
| **Suggest** | (referenced) | Query suggestions | Query discovery |

### Analysis

The Query Agent is Weaviate's agentic AI layer — it bridges natural language and structured database operations. The Ask mode is optimized for end-user chat experiences (returns an LLM-generated answer with sources), while Search mode is optimized for developer/retrieval use cases (returns raw objects). The `filtering` parameter ("recall" vs "precision") is a key tradeoff: "recall" generates multiple query interpretations to maximize coverage (useful for exploratory queries), while "precision" generates a single, most-likely query (faster, better for specific lookups). The `additional_filters` mechanism lets developers constrain the agent's search space (e.g., "only search products in category X") while letting the agent handle the natural language part. The streaming API with `ProgressMessage` updates provides transparency into the agent's reasoning process (query_analysis → search → aggregation → final_answer). The `view_properties` restriction on `QueryAgentCollectionConfig` is a security/privacy feature — it limits which properties the agent can see, preventing it from reasoning about sensitive fields. The pagination via `.next()` reusing the same underlying searches is elegant — it ensures consistency across pages.

### Weaviate Embeddings (Managed Service)

Weaviate Cloud offers a managed embedding inference service (`Weaviate Embeddings`) that simplifies embedding creation without managing multiple provider API keys or rate limits.

### Analysis

The modular architecture is one of Weaviate's strongest differentiators. Unlike systems where the embedding model is baked in, Weaviate lets you mix and match — e.g., OpenAI for embeddings, Cohere for reranking, Anthropic for generation, all on the same collection. The query-time `generative_provider` override enables A/B testing different LLMs without schema changes — invaluable for cost optimization (use a cheaper model for simple queries, a better model for complex ones). The `X-<PROVIDER>-API-KEY` header pattern means all model calls are authenticated at the connection level, not per-query. The self-hosted `text2vec-transformers` and `ner-transformers` modules run in isolated containers — you can deploy them on GPU hardware while running Weaviate itself on CPU-only infrastructure.

## 19. Boost — Soft Ranking (Preview)

### Main Concepts

Boost (v1.38 preview) is a lightweight result reordering mechanism that doesn't require an external model. It promotes or demotes matching documents based on:
- **Property values** (e.g., priority, category)
- **Recency** (time-based decay)
- **Popularity** (numeric decay)
- **Soft filters** (non-strict criteria)

### How Boost Works

Boost runs **after** the initial search and reranking. Matching documents are moved up in ranking; non-matching documents stay but rank lower. This is a "soft" ranking — unlike filters, it doesn't exclude documents, just reorders them.

### Boost in Different Search Types

| Search Type | When Boost Runs |
|---|---|
| Vector search (`near_text`, `near_vector`) | After retrieval |
| BM25 | After retrieval |
| Hybrid | After fusion (the BM25 and vector sub-searches do not see the boost; alpha blend runs first, then boost rescores the fused candidates) |

### Relationship to Rerank

Boost and Rerank are independent — both can be applied. Boost is lightweight (no external model call), while Rerank uses a cross-encoder model. Boost is for simple value-based reordering; Rerank is for semantic relevance refinement.

### Analysis

Boost fills a gap between filtering (hard exclusion) and reranking (expensive model-based reordering). It enables use cases like "show me recent articles first" (time decay), "promote featured products" (property value), or "favor popular items" (numeric decay) without an extra API call to a reranker model. The hybrid search behavior (boost runs after fusion, not on sub-searches) is the correct design — boosting the fused result set is what users expect, not boosting individual keyword/vector legs independently.

## 20. Storage & Persistence Architecture

### Main Concepts

Weaviate is a persistent, fault-tolerant database. Understanding its storage architecture is key to optimizing performance and resource planning.

### Storage Hierarchy

```
Index (per collection)
  └── Shard(s)
        ├── Object Store (LSM-Tree)
        ├── Inverted Index Store (LSM-Tree)
        └── Vector Index (HNSW / Flat / Dynamic / HFresh)
```

### Shard Components

| Component | Storage Technology | Description |
|---|---|---|
| **Object Store** | LSM-Tree (since v1.5) | Stores JSON objects. Memtable → disk segments → merged segments. Bloom filters for lookup. |
| **Inverted Index Store** | LSM-Tree (since v1.5) | Stores property indices for filtering and BM25. Roaring bitmaps for filterable, map index for searchable. |
| **Vector Index** | HNSW (in-memory) | Graph-based vector index. Uses WAL + snapshots for persistence. |

### LSM-Tree Storage

- Data is ingested at memory speed into a **memtable**
- When threshold met, memtable flushed to a **disk segment** (sorted)
- Smaller segments periodically **merged** into larger segments (background)
- **Bloom filters** avoid checking segments that don't contain the target object
- Segments remove outdated versions (from deletes/updates)
- Write-Ahead Log (WAL) ensures durability — every acknowledged write has a WAL entry

### Persistence & Crash Recovery

| Mechanism | Purpose |
|---|---|
| **Write-Ahead Log (WAL)** | Every operation written to append-only log before success response. Crash recovery by replaying WAL. |
| **HNSW Snapshots** (v1.31, default v1.36) | Point-in-time HNSW state. Loaded at startup to skip WAL replay. New snapshots created at startup if changes exist. |

### Lazy Shard Loading

At startup, Weaviate loads all shards. **Lazy shard loading** allows background loading so queries can start sooner.

| Environment Variable | Default | Description |
|---|---|---|
| `LAZY_LOAD_SHARD_COUNT_THRESHOLD` | 1000 | Shard count threshold for auto lazy loading (multi-tenant) |
| `LAZY_LOAD_SHARD_SIZE_THRESHOLD_GB` | 100 | Shard size threshold (GB) |
| `HNSW_STARTUP_WAIT_FOR_VECTOR_CACHE` | true | Vector cache prefill: `true` = synchronous, `false` = async |

- Multi-tenant collections exceeding **either** threshold use lazy loading
- Single-tenant collections always eagerly loaded (unless threshold set to 0)
- For lazy-loaded collections, vector cache prefill is always async

### Asynchronous Indexing

| Version | Behavior |
|---|---|
| v1.22–v1.27 | Async indexing for batch imports only (in-memory queue) |
| v1.28+ | Async indexing for all operations (single imports, deletes, updates). Persistent on-disk queue. |

Enable with `ASYNC_INDEXING=true`. Object store updates quickly; vector index updates in background. Short delay between object creation and vector search availability.

### Time to Live (TTL, v1.36)

Objects can be set to expire after a predetermined time (in seconds). TTL can be relative to a `DATE` property. Expired objects auto-deleted at scheduled intervals. For multi-tenant collections, deletions only occur for active tenants.

### Analysis

The LSM-Tree storage architecture (since v1.5) is the foundation of Weaviate's write performance — data is ingested at memory speed, with background segment merging keeping read performance high. The separation of object store, inverted index, and vector index within each shard (with the vector index being in-memory while object/inverted stores use disk-backed LSM) is a pragmatic design that exploits the different access patterns of each component. The WAL + HNSW snapshot combination ensures both durability and fast startup — the WAL guarantees no acknowledged write is lost, while snapshots (enabled by default in v1.36) dramatically reduce startup time for large indexes by avoiding full WAL replay. The lazy shard loading with auto-detection (v1.36.6) is important for multi-tenant deployments with thousands of tenants — eager loading all shards at startup would take too long, so the auto-detection based on shard count and size thresholds is a sensible heuristic.

### Key Design Principles

1. **Three-API architecture** — REST (management), GraphQL (search), gRPC (performance). Client libraries auto-negotiate the optimal protocol.
2. **Modular model integration** — Vectorizer, generative, and reranker modules are pluggable. 20+ providers supported. Models swappable at query time.
3. **Hybrid search as first-class** — BM25 + vector fusion built into the database, not bolted on. Two fusion algorithms with tunable alpha weighting.
4. **Pre-filtering with ACORN** — Efficient filtered vector search without brute-force fallback. Inverted index + HNSW combination enables pre-filtering that maintains recall.
5. **Multiple index types** — HNSW (default, scalable), Flat (small data), Dynamic (auto-scaling), HFresh (memory-efficient disk-backed). Choose per-collection based on workload.
6. **Training-free compression** — RQ (Rotational Quantization) achieves 4x-32x compression with 98-99% recall without any training phase. PQ/BQ/SQ available for higher compression with training.
7. **Native multi-tenancy** — Per-tenant sharding with 50,000+ active shards per node. Auto-tenant creation, tenant lifecycle (active/inactive/offloaded).
8. **Integrated RAG** — `generate.*` methods combine search + generation in one call. Single prompt (per-object) and grouped task (per-group) modes. Multimodal support (images in prompts).
9. **Built-in Query Agent** — Natural language → database operations. Ask mode (answer), Search mode (raw objects), streaming, async, additional filters, pagination.
10. **LSM-Tree persistence** — Write-optimized storage with WAL + HNSW snapshots for durability and fast startup. Lazy shard loading for large multi-tenant deployments.
11. **Named vectors** — Multiple vector spaces per collection, each with independent vectorizer, index, and compression. Enables multi-model search on the same data.
12. **Tunable consistency** — `ALL`, `QUORUM` (default), `ONE` for replicated collections, enabling consistency-latency tradeoffs per query.
