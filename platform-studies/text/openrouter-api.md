# OpenRouter API Analysis — Text Generation & Conversation Capabilities

> **Base URL:** `https://openrouter.ai/api/v1` | **Docs:** `https://openrouter.ai/docs/quickstart` | **Auth:** Bearer token (`OPENROUTER_API_KEY`)
> **SDKs:** `@openrouter/sdk` (TypeScript), `openrouter` (Python), `@openrouter/agent` (Agent SDK — excluded here), Go SDK | **Compatibility:** OpenAI-compatible (OpenAI SDK works as drop-in via `baseURL`)
> **OpenAPI spec:** `https://openrouter.ai/openapi.yaml` / `https://openrouter.ai/openapi.json`
> **Description:** OpenRouter is a unified gateway + router in front of 400+ models from 70+ providers, exposed through a single OpenAI-compatible endpoint. It normalizes the request/response schema across all models and providers, automatically handles fallbacks, and selects the most cost-effective serving endpoint. Text and conversation capabilities are exposed through four API surfaces — **Chat Completions** (`/api/v1/chat/completions`, primary), **Responses API** (`/api/v1/responses`, OpenAI-compatible, Beta), **Anthropic Messages API** (`/api/v1/messages`), and **Embeddings** (`/api/v1/embeddings`). Tool/function calling, server tools, the Agent SDK, and MCP are explicitly excluded from this analysis and will be covered separately.

## 1. Platform Overview & Core Concepts

### Main Concepts

OpenRouter's text/conversation platform is organized around these core abstractions:

- **Model** — A specific LLM identified by a slug of the form `author/model` (e.g. `openai/gpt-5.2`, `anthropic/claude-sonnet-4.5`). The slug may carry **variant suffixes** (`:nitro`, `:floor`, `:thinking`, `:online`, `:free`, `:extended`) or **latest aliases** (`~openai/gpt-latest`). Browse via `GET /api/v1/models` or [openrouter.ai/models](https://openrouter.ai/models).
- **Provider** — A backend hosting one or more models (e.g. OpenAI, Anthropic, DeepInfra, Together, Google Vertex). The same model may be served by multiple providers; OpenRouter routes between them.
- **Endpoint** — A specific provider hosting instance for a model, possibly region- or tier-specific (e.g. `google-vertex/us-east5`, `deepinfra/turbo`). The finest routing granularity.
- **Message** — A unit of conversation context: `role` (`system` / `user` / `assistant` / `tool` / `developer`) + `content` (string or array of content parts). OpenRouter normalizes this shape across all providers.
- **Content Part** — A typed piece of message content: `text`, `image_url` (URL or base64). Multimodal inputs are expressed as content-part arrays on `user` messages.
- **Response / Choice** — The object returned. `choices[]` is always an array (normalized). Each choice has `message` (non-streaming) or `delta` (streaming), plus a normalized `finish_reason` and the raw `native_finish_reason`.
- **Reasoning Tokens** — Internal "thinking" tokens generated by reasoning models. Counted and billed as output tokens. Surfaced via the `reasoning` field on messages and the `reasoning_details` array.
- **Generation** — A single completed request, identified by an `id` (`gen-...`) returned in the response (and the `X-Generation-Id` header). Stats are queryable after the fact via `/api/v1/generation`.
- **Router** — OpenRouter's per-request decision logic: which model and which provider/endpoint handle the request. Distinct from the gateway (the unified access point).
- **Plugin** — A request/response transform that always runs once when enabled (e.g. response healing, context compression). Distinct from server tools (which the model may call 0–N times).
- **Preset** — A named, server-side configuration (model, fallbacks, provider rules, parameters, system prompt) referenced by slug, so routing lives in one place without redeploying.

### Text & Conversation Tasks

| Task | Description | Primary API |
|------|-------------|-------------|
| **Text generation** | Generate text from a prompt or message history | Chat Completions / Responses |
| **Multi-turn conversation** | Maintain context across turns (stateless — replay history each request) | All chat surfaces |
| **Structured output** | Force JSON conforming to a JSON Schema | Chat Completions / Responses (`response_format`) |
| **Reasoning / thinking** | Control internal reasoning effort and view reasoning tokens | Chat Completions / Responses (`reasoning`) |
| **Streaming** | Receive generation incrementally via SSE | All chat surfaces |
| **Assistant prefill** | Ask the model to complete a partial assistant response | Chat Completions / Messages |
| **Embeddings** | Generate vector representations of text/images | Embeddings |
| **Routing / fallbacks** | Automatic failover between models and providers | Chat Completions / Responses / Messages |
| **Prompt caching** | Cache prompt prefixes to reduce cost/latency | All chat surfaces |

### Platform Architecture

```
Client ──▶ OpenRouter Gateway (https://openrouter.ai/api/v1)
             │  auth, rate limiting, guardrails, observability
             ▼
          Router (per-request decision)
             │  ┌─ model fallbacks (models[] array)
             │  ├─ provider routing (provider{} prefs)
             │  └─ router slugs (openrouter/auto, openrouter/free, ...)
             ▼
          Normalization layer (OpenAI Chat schema)
             │  transforms request/response per provider
             ▼
          Provider endpoint (70+ providers, 400+ models)
             │  fallback on 5xx / rate-limit / moderation
             ▼
          Normalized Response
             choices[].message | delta
             usage (native tokenizer counts, cost)
             openrouter_metadata (routing context, opt-in)
```

## 2. API Surfaces — Chat Completions, Responses, Messages, Embeddings

OpenRouter exposes four API formats, all sharing one auth and one gateway. OpenRouter **normalizes** the schema so the same client code works across all models.

### Key Differences

| Concept | Chat Completions | Responses API (Beta) | Anthropic Messages | Embeddings |
|---------|------------------|----------------------|--------------------|------------|
| **Endpoint** | `POST /api/v1/chat/completions` | `POST /api/v1/responses` | `POST /api/v1/messages` | `POST /api/v1/embeddings` |
| **Format** | OpenAI Chat | OpenAI Responses | Anthropic Messages | OpenAI Embeddings |
| **Input** | `messages[]` | `input` (string or typed item array) | Anthropic `messages[]` + `system` | `input` (string or string[]) |
| **Output** | `choices[].message` | `output[]` typed items | Anthropic message | `data[].embedding` |
| **Stateful** | No (stateless) | No (explicitly stateless) | No | N/A |
| **Streaming** | `delta` chunks (SSE) | Typed SSE events (`response.*`) | SSE | Not supported |
| **Structured outputs** | `response_format` | supported | native | N/A |
| **Reasoning** | `reasoning` param | `reasoning` param | `reasoning` / `thinking` | N/A |
| **Model fallbacks** | `models[]` | `models[]` | `fallbacks[]` (Anthropic shape) | `provider` prefs |
| **Status** | Stable (primary) | Beta | Stable | Stable |

### Chat Completions (primary surface)

The most direct way to use OpenRouter. OpenAI-compatible; the OpenAI SDK works by swapping `baseURL` to `https://openrouter.ai/api/v1`. Supports `messages` or legacy `prompt` (either is required).

### Responses API (Beta)

OpenAI-compatible drop-in for OpenAI's Responses API. **Stateless** — each request is independent; full conversation history must be replayed each turn. Supports reasoning, (tool calling — excluded here), and web search. Returns typed `output[]` items (`message`, `reasoning`, etc.).

### Anthropic Messages API

Lets Anthropic-native clients (e.g. Claude Code) speak their native protocol directly to OpenRouter via `ANTHROPIC_BASE_URL = https://openrouter.ai/api`. Handles model mapping and passes through "Thinking" blocks. Fallbacks use Anthropic's `fallbacks[]` shape (mapped to OpenRouter's `models` routing) — max 3 entries, `model` field only.

### SDK Options

| SDK | Package | Notes |
|-----|---------|-------|
| **TypeScript** | `@openrouter/sdk` | Type-safe, auto-generated types from OpenAPI |
| **Python** | `openrouter` | Thin layer over REST |
| **Agent SDK** | `@openrouter/agent` | `callModel` with multi-turn loops — excluded here |
| **Go** | OpenRouter Go SDK | Community/official |
| **OpenAI SDK** | `openai` (any language) | Drop-in via `baseURL` |
| **Anthropic SDK** | `@anthropic-ai/sdk` | Drop-in via `baseURL` for Messages API |

### Optional Identification Headers

| Header | Purpose |
|--------|---------|
| `HTTP-Referer` | App site URL — for OpenRouter leaderboard rankings |
| `X-OpenRouter-Title` / `X-Title` | App title — for rankings |
| `X-OpenRouter-Categories` | Marketplace categories |
| `X-OpenRouter-Metadata` | `enabled` — surfaces routing metadata under `openrouter_metadata` |
| `X-Generation-Id` | (Response header) generation ID for debugging/correlation |
| `x-session-id` | Sticky routing key (also accepted in request body as `session_id`) |

## 3. Text Generation

### Main Concepts

Text generation is the foundational capability — sending a prompt or message history and receiving model-generated text. OpenRouter normalizes the response to the OpenAI Chat shape: `choices` is always an array, each choice has `message` (or `delta` when streaming). The `model` field in the response names the model that **actually** served the request (which may differ from the requested slug when routing/fallbacks occur).

### API Functions & Parameters

#### Chat Completions — `POST /api/v1/chat/completions`

| Parameter | Type | Description |
|-----------|------|-------------|
| `messages` | Message[] | **Required** (or `prompt`). Conversation history. |
| `prompt` | string | **Required** (or `messages`). Legacy text-completion input. |
| `model` | string | Model slug (e.g. `openai/gpt-5.2`). If omitted, uses user/payer default. |
| `models` | string[] | Fallback model list (see §9). |
| `stream` | boolean | Enable SSE streaming (default `false`). |
| `max_tokens` | integer | Max tokens to generate (deprecated; some providers enforce min 16). |
| `max_completion_tokens` | integer | Preferred max tokens. |
| `temperature` | float | 0.0–2.0, default 1.0. |
| `top_p` | float | 0.0–1.0, default 1.0. |
| `reasoning` | object | Reasoning config (see §6). |
| `response_format` | object | Structured outputs (see §7). |
| `plugins` | Plugin[] | Request/response transforms (see §13). |
| `provider` | object | Provider routing prefs (see §9). |
| `session_id` | string | Sticky routing key (max 256 chars). |
| `stop` | string \| string[] | Stop sequences (up to 4). |
| `seed` | integer | Deterministic sampling (not guaranteed for all models). |
| `user` | string | Stable end-user identifier (abuse detection). |
| `modalities` | enum[] | Output modalities: `text`, `image`, `audio`. |
| `service_tier` | enum | `auto` / `default` / `flex` / `priority` / `scale`. |
| `prediction` | object | `{ type: "content", content: string }` — predicted output for latency reduction. |
| `cache_control` | object | Top-level automatic prompt caching (see §11). |
| `metadata` | object | Key-value pairs (max 16, 64-char keys, 512-char values). |
| `debug` | object | `{ echo_upstream_body: true }` — streaming only. |

See §5 for the full sampling-parameter catalog.

#### Responses API — `POST /api/v1/responses`

| Parameter | Type | Description |
|-----------|------|-------------|
| `model` | string | **Required.** Model slug. |
| `input` | string \| array | **Required.** Plain string or typed item array (`message` items with `content` of `input_text` parts). |
| `stream` | boolean | Enable streaming (default `false`). |
| `max_output_tokens` | integer | Max tokens to generate. |
| `temperature` | float | 0–2. |
| `top_p` | float | 0–1. |
| `reasoning` | object | `{ effort: "minimal"\|"low"\|"medium"\|"high" }` (see §6). |

**Responses API is stateless** — to continue a conversation, include the full prior history (assistant messages require `id` and `status` fields).

### Example (Chat Completions)

```python
from openai import OpenAI

client = OpenAI(
    base_url="https://openrouter.ai/api/v1",
    api_key="<OPENROUTER_API_KEY>",
)

completion = client.chat.completions.create(
    model="~openai/gpt-latest",
    messages=[
        {"role": "user", "content": "What is the meaning of life?"}
    ],
)

print(completion.choices[0].message.content)
```

### Response Shape (Chat Completions, non-streaming)

```json
{
  "id": "gen-xxxxxxxxxxxxxx",
  "choices": [
    {
      "finish_reason": "stop",
      "native_finish_reason": "stop",
      "message": { "role": "assistant", "content": "Hello there!" }
    }
  ],
  "usage": {
    "prompt_tokens": 10,
    "completion_tokens": 4,
    "total_tokens": 14,
    "prompt_tokens_details": { "cached_tokens": 0 },
    "completion_tokens_details": { "reasoning_tokens": 0 },
    "cost": 0.00014
  },
  "model": "openai/gpt-4o"
}
```

### Response Shape (Responses API)

```json
{
  "id": "resp_...",
  "object": "response",
  "model": "openai/o4-mini",
  "output": [
    {
      "type": "message",
      "id": "msg_...",
      "status": "completed",
      "role": "assistant",
      "content": [
        { "type": "output_text", "text": "...", "annotations": [] }
      ]
    }
  ],
  "usage": { "input_tokens": 12, "output_tokens": 45, "total_tokens": 57 },
  "status": "completed"
}
```

### Non-Standard Parameter Handling

If a chosen model doesn't support a request parameter (e.g. `logit_bias` on non-OpenAI models, or `top_k` on OpenAI), the parameter is **ignored** and the rest are forwarded. Provider-specific parameters (e.g. Mistral `safe_prompt`, Hyperbolic `raw_mode`) are transmitted directly to the respective provider.

## 4. Messages, Roles & Content Formats

### Main Concepts

OpenRouter uses the OpenAI Chat message format, normalized across providers. Messages carry a `role` and `content`. Content may be a plain string or, for multimodal user messages, an array of typed content parts.

### Roles

| Role | Description |
|------|-------------|
| `system` | App-level instructions (highest priority). |
| `developer` | Developer instructions (Responses API equivalent of `system`). |
| `user` | End-user input. Supports content-part arrays (text, images). |
| `assistant` | Model-generated output. May carry `tool_calls`, `reasoning`, `reasoning_details`. |
| `tool` | Tool result (carries `tool_call_id`). |

### Message Types (from OpenAPI schema)

- **`system` / `developer`**: `content` string + optional `name`.
- **`user`**: `content` (string or `ContentPart[]`) + optional `name`. Content parts: `{ type: "text", text }` or `{ type: "image_url", image_url: { url, detail? } }`.
- **`assistant`**: `content` string + optional `tool_calls[]`, `reasoning`, `reasoning_details`.
- **`tool`**: `content` string + `tool_call_id` + optional `name`.

### Image Content Parts

```json
{
  "role": "user",
  "content": [
    { "type": "text", "text": "What's in this image?" },
    { "type": "image_url", "image_url": { "url": "https://... or data:image/...;base64,...", "detail": "auto" } }
  ]
}
```

`image_url.url` accepts a URL or base64-encoded image data. `detail` is optional (defaults to `"auto"`).

### Instruction Hierarchy

OpenRouter does not document a strict priority order beyond the OpenAI convention: `system`/`developer` > `user` > `assistant`. The Responses API uses typed `input` items instead of a flat `messages` array.

## 5. Sampling & Generation Parameters

### Main Concepts

Sampling parameters shape token generation. OpenRouter accepts any of these and forwards supported ones to the provider; unsupported ones are silently ignored. Defaults are applied when parameters are absent (e.g. `temperature` defaults to 1.0).

### Full Parameter Catalog

| Parameter | Type | Range / Default | Description |
|-----------|------|------------------|-------------|
| `temperature` | float | 0.0–2.0, default 1.0 | Variety of responses. 0 = deterministic. |
| `top_p` | float | 0.0–1.0, default 1.0 | Nucleus sampling — top tokens summing to P. |
| `top_k` | integer | 0+, default 0 (disabled) | Limit to top K tokens. Not available for OpenAI models. |
| `frequency_penalty` | float | -2.0 to 2.0, default 0.0 | Penalize tokens by occurrence count. Negative encourages reuse. |
| `presence_penalty` | float | -2.0 to 2.0, default 0.0 | Penalize tokens already present (flat, not scaled by count). |
| `repetition_penalty` | float | 0.0–2.0, default 1.0 | Penalize repetition scaled by original probability. |
| `min_p` | float | 0.0–1.0, default 0.0 | Min probability relative to top token (e.g. 0.1 = ≥1/10 of top). |
| `top_a` | float | 0.0–1.0, default 0.0 | Dynamic top-P based on top token probability. |
| `seed` | integer | — | Deterministic sampling (not guaranteed for all models). |
| `max_tokens` | integer | 1+ | Max generation tokens (deprecated; use `max_completion_tokens`). |
| `max_completion_tokens` | integer | 1+ | Max generation tokens. |
| `stop` | string \| string[] | up to 4 | Stop sequences. |
| `logit_bias` | map | token ID → -100..100 | Bias logits before sampling. -100 = ban, 100 = force. |
| `logprobs` | boolean | — | Return log probabilities of output tokens. |
| `top_logprobs` | integer | 0–20 | Number of top tokens per position (requires `logprobs: true`). |
| `modalities` | enum[] | `text`/`image`/`audio` | Output modalities. |
| `verbosity` | enum | `low`/`medium`/`high`/`xhigh`/`max`, default `medium` | Response verbosity (OpenAI Responses API; maps to Anthropic `output_config.effort`). |
| `prediction` | object | `{ type: "content", content }` | Predicted output for latency reduction. |
| `web_search_options` | map | — | Native web search config (provider-dependent). |
| `service_tier` | enum | `auto`/`default`/`flex`/`priority`/`scale` | Cost/latency tier selection. |

## 6. Reasoning / Thinking Tokens

### Main Concepts

Reasoning models (OpenAI o-series / GPT-5, Anthropic Claude with extended thinking, DeepSeek R1, Gemini thinking models, etc.) generate internal **reasoning tokens** ("thinking tokens") before producing output. These are counted and billed as **output tokens**. OpenRouter normalizes the disparate provider mechanisms (OpenAI `reasoning_effort`, Anthropic `thinking`/`budget_tokens`, Google `thinkingLevel`/`thinkingBudget`, Alibaba `thinking_budget`) into a single unified `reasoning` parameter.

Reasoning tokens appear in the `reasoning` field of each message by default (unless excluded), and in the structured `reasoning_details` array. Some models (e.g. OpenAI o-series) do **not** return reasoning tokens even when they use them.

### API Parameters — unified `reasoning` object

```
reasoning: {
  // One of (not both):
  "effort": "max" | "xhigh" | "high" | "medium" | "low" | "minimal" | "none",  // OpenAI-style
  "max_tokens": 2000,  // Anthropic/Gemini/Qwen-style token budget

  // Optional:
  "exclude": false,       // true = use reasoning but don't return it
  "enabled": true,        // enable with default params (medium effort)
  "summary": "concise" | ...,  // summary verbosity
  "context": "auto" | "all_turns" | "current_turn",  // GPT-5.6+ only
  "mode": "standard" | "pro"  // GPT-5.6+ pro variant routing
}
```

### Effort Levels (OpenAI-style)

| Effort | Approx. % of max_tokens for reasoning |
|--------|----------------------------------------|
| `max` / `xhigh` | ~95% |
| `high` | ~80% |
| `medium` | ~50% |
| `low` | ~20% |
| `minimal` | ~10% |
| `none` | Disables reasoning |

For models supporting only `max_tokens`, effort is derived from these ratios; for models supporting only `effort`, `max_tokens` is mapped to an effort level.

### Provider-Specific Mapping

| Provider | Mechanism | Notes |
|----------|-----------|-------|
| **OpenAI** (o-series, GPT-5) | `reasoning.effort` | GPT-5.6+ adds `reasoning.context` and `reasoning.mode: "pro"`. |
| **Anthropic Claude** | `reasoning.max_tokens` (min 1024, max 128000) or `effort` → `budget_tokens` | `:thinking` variant **no longer supported** — use `reasoning` param. Defaults to summarized thinking. `max_tokens` must exceed reasoning budget. |
| **Google Gemini 3** | `reasoning.effort` → `thinkingLevel` | `max_tokens` → `thinkingBudget` (Google re-maps to a level). `xhigh` maps down to `high`. |
| **Gemini 2.5** | `thinkingBudget` | — |
| **Alibaba Qwen** | `reasoning.max_tokens` → `thinking_budget` | Support varies by model. |

### Per-Model Reasoning Discovery

`GET /api/v1/models` returns a `reasoning` object per model:

```json
{
  "reasoning": {
    "supported_efforts": ["high", "medium", "low", "minimal"],
    "default_effort": "medium",
    "default_enabled": true,
    "supports_max_tokens": false,
    "mandatory": true
  }
}
```

`mandatory: true` means reasoning cannot be disabled (`effort: "none"` rejected).

### Preserving Reasoning Across Turns

Pass reasoning back in assistant messages via either:
- `message.reasoning` (string) — plaintext reasoning.
- `message.reasoning_details` (array) — full structured blocks (preserves encrypted/summarized types). The sequence must match the model's original output unmodified.

`reasoning_details` works identically across OpenAI and Anthropic reasoning models, enabling model switching without code changes.

### Reasoning Context Mode (GPT-5.6+)

| `reasoning.context` | Behavior |
|---------------------|----------|
| `auto` (default) | Model's default context mode. |
| `all_turns` | Model references reasoning from all turns in input. |
| `current_turn` | Only current-turn reasoning; prior reasoning ignored. |

### Reasoning Mode (GPT-5.6+)

`reasoning.mode: "pro"` routes to the model's `*-pro` variant (deeper multi-pass reasoning). Independent of `effort`. Bills at same per-token rates but consumes more tokens.

### `reasoning_details` API Shape

Located at `choices[].message.reasoning_details` (non-streaming) or `choices[].delta.reasoning_details` (streaming). Three detail types:

| Type | Fields | Description |
|------|--------|-------------|
| `reasoning.summary` | `summary`, `id`, `format`, `index` | High-level reasoning summary. |
| `reasoning.encrypted` | `data`, `id`, `format`, `index` | Encrypted reasoning (may be `[REDACTED]` in streams). |
| `reasoning.text` | `text`, `signature?`, `id`, `format`, `index` | Raw text reasoning with optional signature. |

`format` values: `unknown`, `openai-responses-v1`, `azure-openai-responses-v1`, `xai-responses-v1`, `anthropic-claude-v1`, `google-gemini-v1`.

### Legacy Parameters (still supported)

- `include_reasoning: true` ≡ `reasoning: {}`
- `include_reasoning: false` ≡ `reasoning: { exclude: true }`
- `reasoning_effort` (top-level) — shorthand for `reasoning.effort`.

## 7. Structured Outputs (JSON Schema & JSON Mode)

### Main Concepts

The `response_format` parameter forces the model to produce specific output formats. OpenRouter supports two modes, normalized across providers. To find supporting models: `GET /api/v1/models?supported_parameters=structured_outputs`.

### API Parameters

#### JSON Schema (strict structured outputs)

```
response_format: {
  "type": "json_schema",
  "json_schema": {
    "name": "weather",
    "strict": true,
    "schema": { ...JSON Schema... }
  }
}
```

The model returns JSON strictly matching `schema`. Always set `strict: true`.

#### JSON Mode (basic)

```
response_format: { "type": "json_object" }
```

Guarantees valid JSON but **not** schema adherence. You must instruct the model to produce JSON via a system/user message.

#### Other `response_format` types (from OpenAPI)

The OpenAPI schema discriminates on `type`: `text`, `json_object`, `json_schema`, `grammar` (CFG constraint), `python`.

### Strict Schema Requirements

When `strict: true`:
- `additionalProperties: false` on every object.
- All fields in `required`.
- Optional fields via union with `null`: `"type": ["string", "null"]`.

### Example

```json
{
  "model": "openai/gpt-4o",
  "messages": [{ "role": "user", "content": "What's the weather in London?" }],
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "weather",
      "strict": true,
      "schema": {
        "type": "object",
        "properties": {
          "location": { "type": "string" },
          "temperature": { "type": "number" },
          "conditions": { "type": "string" }
        },
        "required": ["location", "temperature", "conditions"],
        "additionalProperties": false
      }
    }
  }
}
```

### Model Support

- OpenAI (GPT-4o and later), Google Gemini, Anthropic (Sonnet 4.5, Opus 4.1+), most open-source models, all Fireworks-provided models.

### Ensuring Support

1. Check `supported_parameters` on the model page.
2. Set `provider.require_parameters: true` (only route to providers supporting all params).
3. Include `response_format` with `type: json_schema` in required parameters.

### Streaming with Structured Outputs

Add `stream: true`. The model streams valid partial JSON that, when complete, forms a valid schema-conforming response.

### Error Handling

- **Model doesn't support structured outputs**: request fails with an error.
- **Invalid schema**: model returns an error.
- **Response Healing plugin**: for non-streaming `json_schema` requests, enable the `response-healing` plugin to auto-repair imperfect JSON (see §13).

### `structured_outputs` parameter

Boolean flag indicating the model can return structured outputs via `response_format` `json_schema` — used in model metadata.

## 8. Streaming

### Main Concepts

OpenRouter supports streaming (SSE) from **any** model. Set `stream: true`. The model streams response chunks rather than returning the whole response at once. Useful for chat UIs.

### Chat Completions Streaming

Returns incremental chunks with a `delta` field:
- Text: `delta.content`
- Reasoning: `delta.reasoning_details`
- Usage: returned exactly once in the **final chunk** before `[DONE]` (with an empty `choices` array).

SSE lines are prefixed `data: `. The stream terminates with `data: [DONE]`.

### Responses API Streaming

Returns **typed SSE events** — consumers branch on `type`:

| Event type | Description |
|------------|-------------|
| `response.created` | Response object created. |
| `response.output_item.added` | New output item added. |
| `response.content_part.added` | Content part added. |
| `response.content_part.delta` | Text delta. |
| `response.output_item.done` | Output item complete. |
| `response.reasoning.delta` | Reasoning delta. |
| `response.done` | Response completed (includes `usage`). |
| `[DONE]` | Stream terminator. |

### SSE Comments (Keep-Alive)

OpenRouter occasionally sends SSE comments to prevent timeouts:

```
: OPENROUTER PROCESSING
```

These are spec-compliant comments and can be safely ignored (or used for loading indicators). **Caution**: some SSE clients `JSON.stringify` non-JSON payloads and crash — use `eventsource-parser`, the OpenAI SDK, or the Vercel AI SDK.

### Stream Cancellation

Abort the connection to cancel. For **supported providers** (OpenAI, Anthropic, Azure, DeepInfra, Together, DeepSeek, etc. — but not AWS Bedrock, Groq, Google, Mistral, and others), this immediately stops processing and billing. For unsupported providers or non-streaming requests, the model continues and you are billed for the complete response.

Implementation: pass an `AbortController.signal` (fetch/TS SDK) or close the response (Python `requests`).

### Error Handling During Streaming

| When error occurs | Behavior |
|-------------------|----------|
| **Before any tokens sent** | Standard JSON error response with HTTP status (400/401/402/429/502/503). |
| **After tokens sent (mid-stream)** | Error sent as an SSE event with `error` at top level + `choices[].finish_reason: "error"`. HTTP status stays 200. |

API-specific: OpenAI Chat Completions returns `ErrorResponse` if no chunks processed; OpenAI Responses API may transform `context_length_exceeded` into a success with `finish_reason: "length"`.

## 9. Model Routing — Fallbacks, Providers & Routers

### Main Concepts

OpenRouter is both a **gateway** (unified access point) and a **router** (per-request decision of which model + which provider). Routing happens at two layers:

1. **Model-level** — which model serves the request (`model` + `models[]` fallbacks, or router slugs).
2. **Provider-level** — which provider/endpoint serves the chosen model (`provider{}` preferences).

### Model Fallbacks (`models[]`)

Provide an array of model IDs in priority order. If the primary returns an error, OpenRouter tries the next. Triggers on: context-length errors, moderation flags, rate-limiting, downtime.

```json
{
  "models": ["~anthropic/claude-sonnet-latest", "gryphe/mythomax-l2-13b"],
  "messages": [...]
}
```

You are billed only for the model that actually runs (returned in the `model` response field). With the OpenAI SDK, pass `models` via `extra_body`.

### Anthropic Messages API Fallbacks

The `/api/v1/messages` endpoint accepts Anthropic's `fallbacks[]` shape (mapped to OpenRouter's `models` routing):
- Each entry accepts only the `model` field (per-attempt overrides like `max_tokens`/`thinking`/`speed` are rejected with 400).
- `fallbacks` cannot combine with `models` (400 error).
- Max 3 entries.

### Router Slugs (automatic model selection)

| Slug | Behavior |
|------|----------|
| `openrouter/auto` (Auto Router) | A meta-model routes your prompt to one of dozens of models, optimizing output. Priced at the routed model's rate. |
| `openrouter/free` (Free Models Router) | Routes to available free models. |
| `openrouter/fusion` | Multi-model deliberation (panel + judge). |
| Pareto Router | Picks a coding model by minimum coding score. |

**Session stickiness**: with Auto/Pareto routers, OpenRouter pins the resolved model + provider per conversation (implicit via message-hash fingerprint, or explicit via `session_id`). Prevents the router from switching models each turn.

### Provider Routing (`provider{}`)

Customizes which provider/endpoint serves the chosen model. Default strategy: **price-based load balancing** (weighted by inverse square of price across stable providers, with fallbacks).

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `order` | string[] | — | Provider slugs to try in order (e.g. `["anthropic", "openai"]`). Disables load balancing. |
| `allow_fallbacks` | boolean | `true` | Allow backup providers when primary unavailable. |
| `require_parameters` | boolean | `false` | Only use providers supporting all request parameters. |
| `data_collection` | `"allow"` \| `"deny"` | `"allow"` | `deny` = only providers that don't store/train on data. |
| `zdr` | boolean | — | Restrict to Zero Data Retention endpoints. |
| `enforce_distillable_text` | boolean | — | Restrict to models allowing text distillation. |
| `only` | string[] | — | Provider slugs to allow. |
| `ignore` | string[] | — | Provider slugs to skip. |
| `quantizations` | string[] | — | Filter by quantization (e.g. `["int4", "int8"]`). |
| `sort` | string \| object | — | `"price"` / `"throughput"` / `"latency"`, or `{ by, partition }`. Disables load balancing. |
| `preferred_min_throughput` | number \| object | — | Min throughput (tokens/sec); number = p50, or `{ p50, p75, p90, p99 }`. Deprioritizes (not excludes) non-meeting endpoints. |
| `preferred_max_latency` | number \| object | — | Max latency (sec); same percentile options. |
| `max_price` | object | — | Max pricing; **prevents** request from running if unavailable. |

### Sort Partition

When using `models[]` fallbacks, `sort.partition` controls grouping:
- `"model"` (default): primary model's endpoints tried first regardless of performance.
- `"none"`: endpoints sorted globally across all models — useful for "best performance right now" or "cheapest across models meeting a threshold".

### Provider Slug Matching

- Base slug (e.g. `"google-vertex"`) matches **all** endpoints (every region/variant).
- Full slug (e.g. `"google-vertex/us-east5"`, `"deepinfra/turbo"`) targets a specific endpoint.
- Service-tier endpoints (`openai/priority`, `google-vertex/flex`) are **not** matched by base slugs — require explicit opt-in.

### Tool-Calling & Max-Token Routing Constraint

When you send `tools` or `tool_choice`, OpenRouter only routes to providers supporting tool use. When you set `max_tokens`, it only routes to providers supporting a response of that length.

### Auto Exacto

For tool-calling requests, Auto Exacto orders providers by tool-call success rate (Tool Call Error Rate on model pages).

### Main Concepts

| Variant | Suffix | Equivalent to | Status |

## 11. Prompt Caching

### Main Concepts

Prompt caching reduces cost/latency by reusing cached prompt prefixes. Most providers enable it automatically; some (Anthropic, Alibaba, Gemini) require explicit `cache_control` breakpoints. OpenRouter uses **provider sticky routing** to keep caches warm: after a cached request, subsequent requests for the same model route to the same provider.

### Sticky Routing

- Tracked at account level, per model, per conversation.
- Conversation identified by hashing first system/developer message + first non-system message.
- `session_id` (request body or `x-session-id` header, max 256 chars) overrides the hash as the sticky key — activates on first successful request, even before cache usage observed.
- Only used when cache-read pricing is cheaper than regular prompt pricing.
- Disabled when you set `provider.order` (explicit ordering takes priority).
- With router models (Auto/Pareto), also pins the resolved model.

### Cache Control (explicit breakpoints)

```
cache_control: { "type": "ephemeral" }          // 5-minute TTL (default)
cache_control: { "type": "ephemeral", "ttl": "1h" }  // 1-hour TTL
```

- **Top-level** `cache_control`: automatic caching (system applies breakpoint to last cacheable block; advances as conversation grows). Supported on Anthropic, Google Vertex, Azure, Claude Platform on AWS (not Bedrock InvokeModel/Converse).
- **Per-block** `cache_control` on content parts: explicit breakpoints (max 4 for Anthropic). Works across all Anthropic-compatible providers including Bedrock/Vertex.

### Provider Cache Behavior

| Provider | Mode | Cache write | Cache read | Min tokens |
|----------|------|-------------|------------|------------|
| **OpenAI** | Automatic | Free | 0.25×–0.50× input | 1024 |
| **OpenAI** (Responses API, explicit) | `prompt_cache_breakpoint` + `prompt_cache_options` | 1.25× input | Discounted read rate | GPT-5.6+ only, 30-min TTL |
| **Anthropic** | Automatic (top-level) or explicit (per-block) | 1.25× (5-min) / 2× (1-hr) | 0.1× input | 1024–4096 (varies by model) |
| **DeepSeek** | Automatic | Same as input | 0.1× input | — |
| **Google Gemini 2.5** | Implicit (automatic) | Input + 5-min storage | 0.25× input | 1024 (Flash) / 4096 (Pro) |
| **Google Gemini (explicit)** | `cache_control` breakpoints | Input + storage | 0.25× input | — |
| **Alibaba Qwen** | Explicit `cache_control` only | 1.25× input (5-min TTL) | 0.1× input | — |
| **Groq** | Automatic | Free | 0.5× input | Kimi K2 |
| **Grok** | Automatic | Free | 0.25× input | — |
| **Moonshot** | Automatic | Free | 0.25× input | — |

### Inspecting Cache Usage

- `usage.prompt_tokens_details.cached_tokens` — tokens read from cache (cache hit).
- `usage.prompt_tokens_details.cache_write_tokens` — tokens written to cache.
- Activity page detail button, or `/api/v1/generation` API.
- `cache_discount` field shows savings.

### Responses API Caveat

The Responses API only supports **automatic caching** via top-level `cache_control`. Explicit per-block breakpoints inside `input` items are **not** exposed — use Chat Completions or Anthropic Messages for fine-grained breakpoints.

## 12. Response Caching

### Main Concepts

Distinct from provider prompt caching: OpenRouter caches **entire identical API responses** at the gateway level (before the call reaches a provider). Cache hits are free (all usage counters zeroed).

### Supported Endpoints

| Endpoint | Format |
|----------|--------|
| `/api/v1/chat/completions` | OpenAI Chat Completions |
| `/api/v1/responses` | OpenAI Responses |
| `/api/v1/messages` | Anthropic Messages |
| `/api/v1/embeddings` | OpenAI Embeddings |

Cache keys include an endpoint-type discriminator (no cross-endpoint collision).

### Request Headers

| Header | Value | Description |
|--------|-------|-------------|
| `X-OpenRouter-Cache` | `true` | Enable caching for this request. |
| `X-OpenRouter-Cache` | `false` | Disable (overrides preset). |
| `X-OpenRouter-Cache-TTL` | seconds | Custom TTL (1–86400, default 300). |
| `X-OpenRouter-Cache-Clear` | `true` | Force cache refresh. |

### Limitations

- No request coalescing: concurrent identical requests both MISS and bill independently.
- Provider prompt caching (Anthropic, OpenAI) is separate and can be used together with response caching.

## 13. Plugins (Request/Response Transforms)

### Main Concepts

Plugins extend any model by injecting or mutating a request/response. Unlike server tools (model-callable, 0–N times), plugins **always run once** when enabled. Configurable per-request or as account defaults (Settings → Plugins, with optional "Prevent overrides").

### Available Plugins

| Plugin ID | Description |
|-----------|-------------|
| `web` | Web search (deprecated — use `openrouter:web_search` server tool). |
| `file-parser` | PDF parsing/extraction (`pdf.engine: "cloudflare-ai"`). |
| `response-healing` | Auto-repair malformed JSON responses. |
| `context-compression` | Middle-out truncation when prompts exceed context window (`engine: "middle-out"`). |
| `pareto-router` | Default coding quality tier for Pareto router (`min_coding_score`, `price_source`). |
| `auto-router` | Auto-router config (`allowed_models` w/ wildcards, `cost_quality_tradeoff` 0–10 default 7). |
| `fusion` | Multi-model deliberation (`analysis_models` ≤8, `model` judge, `max_tool_calls` ≤16, `preset`, `tools`). |
| `moderation` | Content moderation. |
| `web-fetch` | URL content fetching (`allowed_domains`, `blocked_domains`, `max_content_tokens`, `max_uses`). |

### Enabling Plugins

```json
{
  "plugins": [
    { "id": "web", "max_results": 3 },
    { "id": "response-healing" }
  ],
  "response_format": { "type": "json_schema", "json_schema": { ... } }
}
```

### Plugin Precedence

1. Request-level `plugins[]` (overrides account defaults).
2. Account defaults (Settings → Plugins).
3. "Prevent overrides" toggled on → account config cannot be overridden by requests.

### Disabling a Default Plugin Per-Request

```json
{ "plugins": [ { "id": "web", "enabled": false } ] }
```

### Model-Variant Shortcuts

- `:online` ≡ `plugins: [{ id: "web" }]` (deprecated).

## 14. Assistant Prefill

### Main Concepts

OpenRouter supports asking models to **complete a partial assistant response** — useful for guiding the model's response direction.

### Usage

Include a message with `role: "assistant"` at the **end** of the `messages` array:

```json
{
  "model": "openai/gpt-5.2",
  "messages": [
    { "role": "user", "content": "What is the meaning of life?" },
    { "role": "assistant", "content": "I'm not sure, but my best guess is" }
  ]
}
```

The model continues from the partial assistant content.

## 15. Embeddings

### Main Concepts

Embeddings are numerical vector representations of text (and, for some models, images) capturing semantic meaning. OpenRouter provides a unified `/api/v1/embeddings` endpoint across multiple embedding-model providers. Use cases: RAG, semantic search, recommendations, clustering, duplicate detection, anomaly detection.

### API Function — `POST /api/v1/embeddings`

| Parameter | Type | Description |
|-----------|------|-------------|
| `model` | string | **Required.** Embedding model slug (e.g. `openai/text-embedding-3-small`). |
| `input` | string \| string[] \| object[] | **Required.** Text, array of texts, or multimodal content blocks. |
| `encoding_format` | string | e.g. `"float"`. |
| `provider` | object | Provider routing prefs (same shape as chat). |

### Batch Processing

Pass an array of strings to generate embeddings for multiple texts in one request (reduces latency/cost).

### Image / Multimodal Input

Some models (e.g. `nvidia/llama-nemotron-embed-vl-1b-v2`) accept image inputs via content blocks:

```json
{
  "model": "nvidia/llama-nemotron-embed-vl-1b-v2",
  "input": [
    {
      "content": [
        { "type": "image_url", "image_url": { "url": "https://..." } }
      ]
    }
  ],
  "encoding_format": "float"
}
```

Text + image can be combined in one input block for a joint embedding.

### Response Shape

```json
{
  "data": [
    { "embedding": [0.1, -0.2, ...], "index": 0 }
  ],
  "usage": { "prompt_tokens": 10, "total_tokens": 10 }
}
```

`response.data[i].embedding` is the vector; dimensionality varies by model.

### Listing Embedding Models

```
GET /api/v1/embeddings/models
GET /api/v1/models?output_modalities=embeddings
```

### Limitations

- **No streaming** — embeddings return as complete responses.
- **Deterministic** — same input always yields identical vectors (no temperature).
- Token limits per model; long texts may need chunking/truncation.

### Best Practices

- Batch requests; cache embeddings (deterministic); use cosine similarity for comparison; chunk long documents meaningfully (paragraphs/sections).

## 16. Models API (Catalog & Metadata)

### Main Concepts

`GET /api/v1/models` returns standardized metadata for all 400+ models. Cached at the edge; designed for production integration. Also available as [RSS feed](https://openrouter.ai/api/v1/models?use_rss=true).

| Parameter | Values | Description |

```
GET /api/v1/model/{author}/{slug}
```

Resolves aliases automatically (e.g. `anthropic/claude-3-5-sonnet` → `anthropic/claude-3.5-sonnet`). Variant suffixes supported (`:free`, `:thinking`). Returns 404 if not found and not an alias.

### Model Object Schema (key fields)

| Field | Type | Description |

| `canonical_slug` | string | Permanent slug. |
| `name` | string | Display name. |
| `context_length` | number | Max context window (tokens). |
| `architecture` | object | `input_modalities[]`, `output_modalities[]`, `tokenizer`, `instruct_type`. |

| `top_provider` | object | `context_length`, `max_completion_tokens`, `is_moderated`. |
| `supported_parameters` | string[] | e.g. `tools`, `tool_choice`, `max_tokens`, `temperature`, `top_p`, `reasoning`, `include_reasoning`, `structured_outputs`, `response_format`, `stop`, `frequency_penalty`, `presence_penalty`, `seed`. |
| `default_parameters` | object \| null | Default parameter values. |
| `reasoning` | object | `supported_efforts`, `default_effort`, `default_enabled`, `supports_max_tokens`, `mandatory`. |
| `expiration_date` | string \| null | Deprecation date. |
| `benchmarks` | object \| undefined | Third-party rankings (e.g. Design Arena ELO). |

### Tokenizer Note

Different models tokenize differently (multi-char chunks vs. per-char). Token counts and costs vary between models even for identical text. Costs are billed per the serving model's native tokenizer.

## 17. Usage, Cost & Generation Stats

### Usage Object (always returned, non-streaming)

```typescript
type ResponseUsage = {
  prompt_tokens: number;        // includes images, audio, tools
  completion_tokens: number;     // generated tokens
  total_tokens: number;
  prompt_tokens_details?: {
    cached_tokens: number;
    cache_write_tokens?: number;
    audio_tokens?: number;
    video_tokens?: number;
  };
  completion_tokens_details?: {
    reasoning_tokens?: number;
    audio_tokens?: number;
    image_tokens?: number;
  };
  cost?: number;                 // credits
  is_byok?: boolean;
  cost_details?: {
    upstream_inference_cost?: number;
    upstream_inference_prompt_cost: number;
    upstream_inference_completions_cost: number;
  };
  server_tool_use?: { web_search_requests?: number };
};
```

Token counts use the model's **native tokenizer**. For streaming, `usage` appears once in the final chunk before `[DONE]`.

### Finish Reason (normalized)

OpenRouter normalizes `finish_reason` to: `tool_calls`, `stop`, `length`, `content_filter`, `error`. The raw provider value is in `native_finish_reason`.

### Querying Generation Stats

```
GET /api/v1/generation?id=$GENERATION_ID
```

Returns token counts and cost asynchronously (useful for auditing historical usage). The generation ID is also in the `X-Generation-Id` response header.

### Billing Notes

- Failed/fallback attempts are **not** billed — you pay only for the successful model run.
- Streaming is billed identically to non-streaming (per token).
- Zero-completion insurance: no charge for zero-token responses.
