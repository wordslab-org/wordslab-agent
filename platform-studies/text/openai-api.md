# OpenAI API Analysis — Text Generation & Conversation Capabilities

> **Base URL:** `https://api.openai.com/v1` | **Docs:** `https://developers.openai.com/api/docs/guides/text` | **Auth:** Bearer token (`OPENAI_API_KEY`)
> **SDKs:** `openai` (Python / TypeScript / .NET / Java / Go / Ruby) | **CLI:** OpenAI CLI (`openai responses create`)
> **Description:** OpenAI exposes text and conversation capabilities through two API surfaces — the legacy **Chat Completions API** (`/v1/chat/completions`) and the newer **Responses API** (`/v1/responses`), the latter being recommended for all new projects. The platform covers text generation from prompts, structured JSON output, function/tool calling, multi-turn conversation state management, and file inputs. Reasoning models (GPT-5.x family) gain richer behavior on the Responses API, including an agentic loop that lets the model call multiple tools within a single request.

## 1. Platform Overview & Core Concepts

### Main Concepts

OpenAI's text/conversation platform is organized around these core abstractions:

- **Model** — The underlying large language model. Two families: **chat models** (e.g. `gpt-4o`) and **reasoning models** (e.g. `gpt-5.6`, `o4-mini`) which internally generate reasoning tokens before producing output. Reasoning models perform better and demonstrate higher intelligence on the Responses API.
- **Prompt** — The input text (and/or structured messages) given to the model to generate a response. Prompt engineering is the process of writing effective instructions for consistent output.
- **Message / Item** — A unit of conversation context. Chat Completions uses *Messages* (`role` + `content`); the Responses API uses typed *Items* (a union of `message`, `reasoning`, `function_call`, `function_call_output`, etc.).
- **Role** — The authority level of a message: `developer` (app-level instructions, highest priority), `user` (end-user input), `assistant` (model-generated output). The `system` role from Chat Completions maps to `developer` in the Responses API.
- **Instructions** — A top-level parameter in the Responses API for high-level system guidance (tone, goals, behavior rules). Takes priority over `input` content. Equivalent to a `developer`-role message.
- **Tool / Function** — External functionality the model can call to access data or take actions outside its training data. Defined by a JSON Schema; the model emits a *tool call* with arguments, the app executes it and returns a *tool call output*.
- **Response** — The object returned by the API. In Chat Completions, it contains `choices[].message`; in Responses, it contains a typed `output` array of Items. Responses are stored by default (30-day TTL) unless `store: false` is set.
- **Conversation** — A long-running, persistent state object (via the Conversations API) that stores items across sessions, devices, or jobs. Alternative to manual state management or `previous_response_id` chaining.
- **Context Window** — The maximum tokens (input + output + reasoning) usable in a single request. Varies by model (e.g. 128k for `gpt-4o`).
- **Reasoning Tokens** — Internal tokens generated by reasoning models to plan a response. Counted against the context window. Can be preserved across turns via encrypted reasoning items.

### Text & Conversation Tasks

| Task | Description | API |
|------|-------------|-----|
| **Text generation** | Generate text (prose, code, JSON, equations) from a prompt | Responses / Chat Completions |
| **Structured output** | Force model output to conform to a JSON Schema | Responses (`text.format`) / Chat Completions (`response_format`) |
| **Function calling** | Let the model call external functions/tools for data or actions | Responses / Chat Completions |
| **Multi-turn conversation** | Maintain context across multiple messages/turns | Responses (stateful) / Chat Completions (manual) |
| **File-based input** | Send PDFs, documents, spreadsheets, code files as model input | Responses / Chat Completions (limited) |
| **Streaming** | Receive generation progress incrementally | Responses (typed SSE events) / Chat Completions (delta chunks) |

### Platform Architecture

```
Chat Completions API (/v1/chat/completions):
  messages[] ──▶ Model ──▶ choices[].message (text/tool_calls)

Responses API (/v1/responses):
  input (string | Item[]) + instructions ──▶ Model ──▶ output[] (typed Items)
                                                │
                    ┌───────────────────────────┼───────────────────────────┐
                    ▼                           ▼                           ▼
              message Items            reasoning Items          function_call Items
              (output_text)            (encrypted_content)      (+ function_call_output)

State management:
  Manual:       append output Items to input on each turn
  previous_response_id: chain stored responses (store: true)
  Conversations API: persistent conversation object (conv_...)
  Encrypted reasoning: store: false + include: ["reasoning.encrypted_content"]
```

## 2. API Surfaces — Chat Completions vs Responses

The Responses API is OpenAI's new recommended API primitive, an evolution of Chat Completions. Chat Completions remains supported but Responses is preferred for all new projects.

### Key Differences

| Concept | Chat Completions | Responses |
|---------|-----------------|-----------|
| **Endpoint** | `POST /v1/chat/completions` | `POST /v1/responses` |
| **Input** | `messages[]` array | `input` (string or array of typed Items) |
| **System guidance** | `messages` with `role: "system"` | Top-level `instructions` parameter |
| **Output** | `choices[].message` | Typed `output` array of Items |
| **Final text helper** | — | `response.output_text` (SDK convenience) |
| **Multiple candidates** | `n` parameter (multiple `choices`) | Not supported; make separate requests |
| **Storage** | Stored by default for new accounts | Stored by default (30-day TTL) |
| **State management** | Manual (replay `messages` each turn) | `previous_response_id`, Conversations API, or manual |
| **Structured Outputs** | `response_format` | `text.format` |
| **Function definition shape** | Externally tagged (`{"type": "function", "function": {...}}`) | Internally tagged (fields at top level: `{"type": "function", "name": ..., "parameters": ...}`) |
| **Function call in output** | `message.tool_calls[]` with `function.name` + `function.arguments` | `function_call` Item with top-level `name`, `arguments`, `call_id` |
| **Function result** | `{"role": "tool", "tool_call_id": ..., "content": ...}` | `{"type": "function_call_output", "call_id": ..., "output": ...}` |
| **Built-in tools** | Not available natively | `tools: [{"type": "web_search" | "file_search" | ...}]` |
| **Streaming** | `delta` chunks | Typed SSE events |
| **Reasoning + `reasoning: none` + tools** | Supported (pre-GPT-5.4) | Required (tool calling unsupported in Chat Completions from GPT-5.4+) |
| **`output_text` SDK helper** | No | Yes |
| **File URLs** | Not supported | Supported |
| **PDF `detail` control** | Not supported | Supported (`auto`/`low`/`high`) |

### Responses API Benefits

- **Better performance**: Reasoning models (GPT-5+) show ~3% improvement on SWE-bench vs Chat Completions with same prompt/setup.
- **Agentic by default**: The Responses API is an agentic loop — the model can call multiple tools (web search, file search, code interpreter, custom functions, remote MCP) within a single API request.
- **Lower costs**: Improved cache utilization (40–80% improvement vs Chat Completions in internal tests).
- **Stateful context**: `store: true` maintains state turn-to-turn, preserving reasoning and tool context.
- **Flexible inputs**: Pass a string or a list of messages; use `instructions` for system-level guidance.
- **Encrypted reasoning**: Opt out of statefulness while still benefiting from advanced reasoning (for ZDR compliance).
- **Future-proof**: Future-proofed for upcoming models.

### Migration Path (Chat Completions → Responses)

1. **Update endpoints**: `POST /v1/chat/completions` → `POST /v1/responses`. Simple message inputs are compatible.
2. **Map Messages to Items**: `messages[]` → `input` (string or Item array). System/dev guidance → top-level `instructions` or developer-role Items.
3. **Update multi-turn logic**: Choose `previous_response_id`, manual Item replay, or Conversations API.
4. **Decide statefulness**: `store: true` (default) for stateful; `store: false` + `include: ["reasoning.encrypted_content"]` for stateless with reasoning.
5. **Update function definitions**: Externally tagged → internally tagged; update tool call/result handling.
6. **Update Structured Outputs**: `response_format` → `text.format`.
7. **Update streaming consumers**: `delta` chunks → typed SSE events.

**Note:** The Assistants API is deprecated as of August 26, 2025, with a sunset date of August 26, 2026.

## 3. Text Generation

### Main Concepts

Text generation is the foundational capability — prompting a model to produce text. The model generates an array of content in the `output` property. The `output` array can contain multiple items: message text, tool calls, reasoning tokens, and other items.

**Critical**: The `output` array often has more than one item. It is **not safe** to assume the model's text is at `output[0].content[0].text`. The SDK `output_text` helper aggregates all text outputs into a single string for convenience.

### API Functions & Parameters

#### Responses API — `POST /v1/responses`

| Parameter | Type | Description |
|-----------|------|-------------|
| `model` | string | **Required.** Model ID (e.g. `gpt-5.6`). |
| `input` | string \| array | **Required.** A prompt string, or an array of input Items (messages with `role` + `content`). |
| `instructions` | string | High-level system instructions (tone, goals, behavior). Takes priority over `input`. Only applies to the current request; not carried over via `previous_response_id`. |
| `reasoning` | object | Reasoning configuration (see §5). |
| `store` | boolean | Whether to store the response (default: `true`). Set `false` for stateless/ZDR. |
| `previous_response_id` | string | ID of a previous response to chain context. Requires `store: true`. |
| `conversation` | string | Conversation ID (`conv_...`) for persistent conversation state. |
| `include` | array | Additional data to include (e.g. `["reasoning.encrypted_content"]`). |
| `tools` | array | Tool definitions (functions, custom tools, built-in tools). |
| `tool_choice` | string \| object | Controls tool usage (see §8). |
| `text` | object | Text format configuration (`text.format` for Structured Outputs). |
| `stream` | boolean | Enable streaming. |

#### Chat Completions API — `POST /v1/chat/completions`

| Parameter | Type | Description |
|-----------|------|-------------|
| `model` | string | **Required.** Model ID. |
| `messages` | array | **Required.** Array of messages (`role` + `content`). |
| `n` | integer | Number of candidate generations (not available in Responses). |
| `tools` | array | Tool definitions. |
| `tool_choice` | string \| object | Controls tool usage. |
| `response_format` | object | Structured Outputs / JSON mode configuration. |
| `stream` | boolean | Enable streaming. |
| `parallel_tool_calls` | boolean | Allow multiple tool calls per turn (default: `true`). |

### Example (Responses API)

```python
from openai import OpenAI
client = OpenAI()

response = client.responses.create(
    model="gpt-5.6",
    input="Write a one-sentence bedtime story about a unicorn."
)

print(response.output_text)
```

### Output Structure (Responses API)

```json
{
  "id": "resp_...",
  "object": "response",
  "created_at": 1756315696,
  "model": "gpt-5.6",
  "output": [
    {
      "id": "rs_...",
      "type": "reasoning",
      "content": [],
      "summary": []
    },
    {
      "id": "msg_...",
      "type": "message",
      "status": "completed",
      "content": [
        {
          "type": "output_text",
          "annotations": [],
          "logprobs": [],
          "text": "Under a quilt of moonlight, a drowsy unicorn..."
        }
      ],
      "role": "assistant"
    }
  ]
}
```

### Prompt Engineering Best Practices

- **Pin model snapshots** in production (e.g. `gpt-5.5-2026-04-23`) for consistent behavior.
- **Build tests/eval suites** to measure prompt performance as you iterate.
- **Store prompts in code**, not as reusable prompt objects (OpenAI is deprecating `v1/prompts`; shutdown scheduled November 30, 2026).
- Keep prompt builders in a small module near the feature they support.
- Use typed function arguments or schemas for dynamic values.
- Add representative fixtures, tests, and evaluation checks before changing production prompts.

## 4. Message Roles & Instruction Hierarchy

### Main Concepts

Messages have differing **levels of authority** following the OpenAI Model Spec chain of command:

| Role | Priority | Description |
|------|----------|-------------|
| `developer` | Highest | Instructions from the application developer. System rules and business logic — like a function definition. |
| `user` | Medium | Instructions from the end user. Inputs and configuration — like function arguments. |
| `assistant` | — | Messages generated by the model. |

The `instructions` parameter (Responses API) is equivalent to a `developer`-role message and takes priority over `input` content.

### API Parameters

- **`instructions`** (Responses API, top-level string): High-level guidance for the current request only. Not carried over when using `previous_response_id` — resend stable instructions on each request.
- **`role`** (in message Items): `"developer"`, `"user"`, or `"assistant"`.

### Example

```python
response = client.responses.create(
    model="gpt-5.6",
    reasoning={"effort": "low"},
    instructions="Talk like a pirate.",
    input="Are semicolons optional in JavaScript?",
)
```

Equivalent using message roles:

```python
response = client.responses.create(
    model="gpt-5.6",
    reasoning={"effort": "low"},
    input=[
        {"role": "developer", "content": "Talk like a pirate."},
        {"role": "user", "content": "Are semicolons optional in JavaScript?"},
    ],
)
```

## 5. Reasoning Configuration

### Main Concepts

Reasoning models (GPT-5.x, o-series) generate internal **reasoning tokens** to plan responses before producing output. These tokens count against the context window. The Responses API provides a richer reasoning experience than Chat Completions, especially for tool usage.

### API Parameters

| Parameter | Location | Description |
|-----------|----------|-------------|
| `reasoning.effort` | `reasoning: { effort: "low" \| "medium" \| "high" }` | Controls how much reasoning the model does. Lower = faster/cheaper; higher = more thorough. |
| `reasoning.summary` | `reasoning: { summary: "auto" \| "concise" \| "detailed" }` | Controls reasoning summary verbosity. |
| `reasoning.context` | `reasoning: { context: "all_turns" }` | For models supporting persisted reasoning, renders reasoning from earlier turns into the next sample. |
| `include` | `["reasoning.encrypted_content"]` | Returns encrypted reasoning tokens for stateless use (ZDR compliance). |
| `store` | boolean | Must be `false` when using encrypted reasoning for stateless operation. |

### Encrypted Reasoning (Stateless + Reasoning)

For Zero Data Retention (ZDR) organizations that cannot use stateful storage:

1. Set `store: false`.
2. Add `["reasoning.encrypted_content"]` to `include`.

The API returns encrypted reasoning tokens that can be passed back in future requests like regular reasoning Items. When included, encrypted content is decrypted in memory, used for generation, then securely discarded. New reasoning tokens are immediately encrypted and returned.

**Note:** OpenAI enforces `store: false` automatically for ZDR organizations.

### Reasoning Items in Multi-Turn

When using reasoning models with tool calls, any reasoning Items returned in model responses **must** be passed back along with tool call outputs. For stateless requests, preserve every Item in `response.output` and use `include: ["reasoning.encrypted_content"]`.

## 6. Structured Outputs (JSON Schema Enforcement)

### Main Concepts

**Structured Outputs** ensures the model will always generate responses that adhere to a supplied JSON Schema. Benefits:

1. **Reliable type-safety** — No need to validate or retry incorrectly formatted responses.
2. **Explicit refusals** — Safety-based model refusals are programmatically detectable.
3. **Simpler prompting** — No need for strongly worded prompts to achieve consistent formatting.

### When to Use Structured Outputs

| Use Case | Mechanism |
|----------|-----------|
| **Connecting model to tools/functions/data** | Function calling with `strict: true` |
| **Structuring the model's response to the user** | `response_format` (Chat Completions) / `text.format` (Responses) |

### API Parameters

#### Chat Completions API

```
response_format: {
  "type": "json_schema",
  "json_schema": {
    "name": "schema_name",
    "strict": true,
    "schema": { ...JSON Schema... }
  }
}
```

SDK helper: `client.chat.completions.parse()` with Pydantic model / Zod schema → `completion.choices[0].message.parsed`.

#### Responses API

```
text: {
  "format": {
    "type": "json_schema",
    "name": "schema_name",
    "strict": true,
    "schema": { ...JSON Schema... }
  }
}
```

Note: In Responses, the `name`, `strict`, and `schema` fields are flattened directly under `format` (no `json_schema` nesting wrapper).

SDK helper: `client.responses.parse()` with Pydantic model / Zod schema → `response.output_parsed`.

### Critical Schema Requirements (Strict Mode)

When `strict: true`:

- **`additionalProperties: false`** is mandatory on every object in the schema.
- **All fields must be in `required`** — every property must appear in the `required` array.
- **Optional fields** are emulated via union with `null`: `"type": ["string", "null"]`.
- **Root object must be an object** — cannot be `anyOf` at the top level.

### Supported JSON Schema Subset

**Supported types:** `string`, `number`, `boolean`, `integer`, `object`, `array`, `enum`, `anyOf`.

**Supported property constraints:**

| Type | Supported constraints |
|------|-----------------------|
| String | `pattern` (regex), `format` (`date-time`, `time`, `date`, `duration`, `email`, `hostname`, `ipv4`, `ipv6`, `uuid`) |
| Number | `multipleOf`, `maximum`, `exclusiveMaximum`, `minimum`, `exclusiveMinimum` |
| Array | `minItems`, `maxItems` |

**Supported features:**
- **`$defs` / `$ref`** — reusable subschemas via `#/$defs/...`
- **Recursive schemas** — root recursion via `$ref: "#"` and explicit recursion via `$defs`
- **`anyOf`** — each nested schema must individually be valid

**Unsupported keywords:** `allOf`, `not`, `dependentRequired`, `dependentSchemas`, `if`, `then`, `else`.

**Fine-tuned models — additional unsupported:** `minLength`, `maxLength`, `pattern`, `format` (strings); `minimum`, `maximum`, `multipleOf` (numbers); `patternProperties` (objects); `minItems`, `maxItems` (arrays).

### Size & Nesting Limits

| Limit | Value |
|-------|-------|
| Max object properties (total) | 5,000 |
| Max nesting levels | 10 |
| Max total length of property names, definition names, enum values, const values | 120,000 characters |
| Max enum values (total across all enum properties) | 1,000 |
| For a single string enum with >250 values: max total enum string length | 15,000 characters |

### Output Ordering

Outputs are produced in the same order as keys appear in the schema.

### Refusals Handling

Safety-based refusals are programmatically detectable:

| API | How to detect refusal |
|-----|----------------------|
| Chat Completions | Check `response.choices[0].message.refusal` — if present, it contains the refusal explanation. Check before reading `.content`. |
| Responses API | Check if message content item has `type === "refusal"`; the `.refusal` field holds the explanation. |

### Edge Cases to Handle

| Condition | Chat Completions signal | Responses signal |
|-----------|------------------------|-----------------|
| Incomplete/truncated | `finish_reason === "length"` | `status === "incomplete"` + `incomplete_details.reason === "max_output_tokens"` |
| Content filtered | `finish_reason === "content_filter"` | `status === "incomplete"` + reason `content_filter` |
| Success | `finish_reason === "stop"` | `status === "completed"` |

### Supported Models

Structured Outputs is available starting with `gpt-4o-mini` and `gpt-4o-2024-08-06` and later. For new projects, start with `gpt-5.6`.

### Use Case Examples

1. **Chain of thought** — Structured step-by-step reasoning (steps array + final_answer).
2. **Structured data extraction** — Extract title, authors, abstract, keywords from unstructured text.
3. **UI generation** — Generate JSON that drives distinct UI rendering of different output parts.
4. **Moderation** — Structured classification output.

### Fine-Tuned Model Note

For fine-tuned models, the first request with a given schema has extra latency (schema processing); subsequent requests with the same schema do not. Schemas are cached for performance and are **not eligible for zero data retention**.

## 7. JSON Mode

### Main Concepts

JSON Mode is the older, more basic feature that guarantees valid JSON output but **does not** guarantee schema adherence. Structured Outputs is the recommended evolution.

### API Parameters

| API | Parameter |
|-----|-----------|
| Chat Completions | `response_format: { "type": "json_object" }` |
| Responses | `text: { format: { "type": "json_object" } }` |

### Comparison: Structured Outputs vs JSON Mode

| Feature | Structured Outputs | JSON Mode |
|---------|-------------------|-----------|
| Outputs valid JSON | Yes | Yes |
| Adheres to schema | Yes | No |
| Compatible models | `gpt-4o-mini`, `gpt-4o-2024-08-06`, and later | `gpt-3.5-turbo`, `gpt-4-*`, `gpt-4o-*`, GPT-5 models |
| Enabling | `json_schema` type + `strict: true` | `json_object` type |

### JSON Mode Rules

- You **must** instruct the model to produce JSON somewhere in the conversation (e.g., system message). The API throws an error if the string "JSON" does not appear in the context; otherwise the model may generate an unending stream of whitespace until the token limit.
- Use a validation library + retries if you need schema conformance.
- Function calling always enables JSON mode implicitly.
- Both Structured Outputs and JSON mode are supported in Responses, Chat Completions, Assistants, Fine-tuning, and Batch APIs.

**Recommendation:** Always use Structured Outputs instead of JSON mode when possible.

## 8. Function Calling (Tool Calling)

### Main Concepts

**Function calling** (also **tool calling**) lets models interface with external systems and access data outside their training data.

**Key terms:**

- **Function / Tool** — A piece of functionality the model can access. Defined by a JSON Schema.
- **Function call / Tool call** — A special response from the model indicating it needs to call a tool, with arguments.
- **Function call output / Tool call output** — The result generated by executing the tool, sent back to the model.

**Tool types:**

| Type | Description |
|------|-------------|
| **Function tools** | Defined by a JSON Schema; model returns JSON-encoded `arguments`. |
| **Custom tools** | Free-form text input/output (see §9). |
| **Built-in tools** | OpenAI-hosted: `web_search`, `file_search`, `computer_use`, `code_interpreter`, `image_generation`, remote MCP, `apply_patch`, `local_shell`. Only available in the Responses API. |

### The Tool Calling Flow (5 Steps)

1. Make a request to the model with tools it could call.
2. Receive a tool call from the model.
3. Execute code on the application side with input from the tool call.
4. Make a second request to the model with the tool output.
5. Receive a final response from the model (or more tool calls).

The Responses API can continue this flow for as many tool calls as the task requires within a single agentic-loop request.

### Function Definition Schema

| Field | Description |
|-------|-------------|
| `type` | Always `"function"` |
| `name` | Function name (e.g. `get_weather`) |
| `description` | Details on when and how to use the function |
| `parameters` | JSON Schema defining the function's input arguments |
| `strict` | Whether to enforce strict mode for the function call |

**Chat Completions shape** (externally tagged):
```json
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "Retrieves current weather for the given location.",
    "parameters": { ... },
    "strict": true
  }
}
```

**Responses shape** (internally tagged — fields at top level):
```json
{
  "type": "function",
  "name": "get_weather",
  "description": "Retrieves current weather for the given location.",
  "parameters": { ... },
  "strict": true
}
```

### `strict` Mode

Strict mode ensures function calls reliably adhere to the function schema (powered by Structured Outputs under the hood). **Always recommended.**

**Requirements:** `additionalProperties: false` on every object; all fields in `required`; optional fields via `"type": ["<type>", "null"]`.

**Default behavior differs by API:**

| API | Default `strict` behavior |
|-----|--------------------------|
| Chat Completions | Non-strict by default |
| Responses | Attempts strict normalization; falls back to non-strict best-effort if schema incompatible (response shows `strict: false`). Set `strict: false` explicitly to opt out. |

If `strict: true` is sent with an incompatible schema, the request is rejected with details. All schemas generated in the Playground have strict mode enabled.

### Namespaces

Group related tools by domain (e.g. `crm`, `billing`, `shipping`). Especially useful when the model must choose between tools serving different systems.

```json
{
  "type": "namespace",
  "name": "crm",
  "description": "CRM tools for customer lookup and order management.",
  "tools": [
    {
      "type": "function",
      "name": "get_customer_profile",
      "description": "Fetch a customer profile by customer ID.",
      "defer_loading": true,
      "parameters": { ... }
    }
  ]
}
```

Individual functions within a namespace can set `defer_loading: true` for use with tool search.

### `tool_choice` Parameter

Controls when/how many tools the model uses:

| Value | Behavior |
|-------|----------|
| `"auto"` (default) | Zero, one, or multiple functions |
| `"required"` | One or more functions |
| `"none"` | No functions (imitates passing no tools) |
| `{"type": "function", "name": "get_weather"}` | Exactly one specific function (forced) |
| `{"type": "allowed_tools", "mode": "auto", "tools": [...]}` | Restrict to a subset of available tools (useful for prompt caching savings without modifying the tools list) |

With tool search, `tool_choice` applies to tools currently callable in the turn.

### `parallel_tool_calls` Parameter

| Value | Behavior |
|-------|----------|
| `true` (default) | Model may call multiple functions in a single turn |
| `false` | Ensure exactly zero or one tool is called per turn |

**Constraints:**
- Not possible when using built-in tools.
- On fine-tuned models, if the model calls multiple functions in one turn, strict mode is disabled for those calls.
- `gpt-4.1-nano-2025-04-14` may include duplicate calls for the same tool with parallel calls enabled; disable for that snapshot.

### Handling Function Calls

**Chat Completions:**
- Tool calls in: `completion.choices[0].message.tool_calls` (array with `id`, `type: "function"`, `function: { name, arguments }`).
- Return result: append `{"role": "tool", "tool_call_id": <id>, "content": <result string>}` to messages.

**Responses API:**
- Tool calls in: `response.output` (Items with `type: "function_call"`, `id`, `call_id`, `name`, `arguments`).
- With tool search: may include `tool_search_call` and `tool_search_output` Items before `function_call`.
- Return result: append `{"type": "function_call_output", "call_id": <call_id>, "output": <result string>}` to input.

**Result formatting:**
- Typically a string (JSON, error codes, plain text — your choice).
- For functions returning images/files: pass an array of image/file objects instead of a string.
- For functions with no return value (e.g. `send_email`): return a success/failure string like `"success"`.

### Token Usage

Functions are injected into the system message in a trained syntax, so they count against the context limit and are billed as input tokens. Limit functions, shorten descriptions, or use tool search/fine-tuning to reduce tokens.

### Best Practices for Defining Functions

- Write clear, detailed names, parameter descriptions, and instructions.
- Use the system prompt to describe when to use each function.
- Include edge cases (note: examples may hurt reasoning models).
- Apply software engineering best practices: principle of least surprise, use enums/objects to make invalid states unrepresentable.
- Offload burden from the model — don't make it fill arguments you already know; combine functions always called in sequence.
- Keep initially-available functions small — aim for fewer than 20 at the start of a turn.
- Use tool search to defer large/infrequent tools.
- Leverage Playground for schema generation; consider fine-tuning for large numbers of functions.

### SDK Helpers (Pydantic / Zod)

- **Python:** `from openai import pydantic_function_tool` → `tools = [pydantic_function_tool(GetWeather)]`
- **JS/TS:** `import { zodFunction } from "openai/helpers/zod"` → `zodFunction({ name: "getWeather", parameters: GetWeatherParameters })`

Not all Pydantic/Zod features are supported.

## 9. Custom Tools (Free-Form Text I/O)

### Main Concepts

Custom tools are an alternative to function tools. Instead of providing a JSON Schema describing exact input structure, the model passes an **arbitrary string** back to your tool as input. Useful to avoid wrapping a response in JSON unnecessarily, or to apply a custom grammar to the response.

### API Parameters

| Parameter | Description |
|-----------|-------------|
| `type` | `"custom"` (instead of `"function"`) |
| `name` | Tool name |
| `description` | When/how to use the tool |
| `format` | Optional grammar constraint (see below) |

**No `parameters` schema** — the model generates free-form text as input.

### Tool Call Output

The output Item has `type: "custom_tool_call"` with a plain-text `input` field (instead of `function_call` with JSON `arguments`):

```json
{
  "type": "custom_tool_call",
  "status": "completed",
  "call_id": "call_...",
  "input": "print(\"hello world\")",
  "name": "code_exec"
}
```

### Context-Free Grammars (CFG)

Constrain the model's text input for a custom tool using a CFG:

```
"format": {
  "type": "grammar",
  "syntax": "lark" | "regex",
  "definition": "<grammar string>"
}
```

| Syntax | Description | Limitations |
|--------|-------------|-------------|
| **`lark`** | Variation of Lark; sampling constrained via LLGuidance | No lookarounds in lexer regexes, no lazy modifiers (`*?`, `+?`, `??`), no terminal priorities, no templates, no imports (except built-in `%import` common), no `%declare`s |
| **`regex`** | Rust regex crate syntax (not Python's `re`) | No lookarounds, no lazy modifiers. Pattern must be on one line (use `\n` for newlines; no verbose/extended mode). Provide as plain pattern string (not enclosed in `//`). |

### CFG Best Practices

- Keep grammars simple — the API may reject overly complex grammars.
- Prefer a single, bounded terminal when carving text from freeform spans.
- Don't split free text across rules/terminals (greedy lexer won't respect intended boundaries).
- Use rules to compose discrete tokens, not to steer regex internals.
- Keep terminals simple, bounded, self-contained (prefer `{0,10}` over unbounded `*`).
- Treat whitespace explicitly; avoid unbounded `%ignore` directives.
- If the model drifts out-of-distribution (long/repetitive but syntactically valid output): tighten the grammar, add few-shot examples, improve tool description, or raise reasoning effort.

## 10. Tool Search (Deferred Tool Loading)

### Main Concepts

When you need to give the model access to a large ecosystem of tools, **tool search** lets you defer loading some or all tools. The `tool_search` tool lets the model search for relevant tools, add them to the model context, and then use them.

### API Parameters

- Define tool search as a special tool in the `tools` array.
- Individual functions can set `defer_loading: true` within namespaces.
- Only `gpt-5.4` and later models support `tool_search`.

### Flow

```
1. Request with tool_search + deferred tools
2. Model calls tool_search → relevant tools loaded into context
3. Model calls the now-available function tools
4. Tool outputs returned to model
5. Final response
```

When using tool search, you may see `tool_search_call` and `tool_search_output` Items in `response.output` before `function_call` Items.

## 11. Conversation State Management

### Main Concepts

Each text generation request is independent and stateless by default. OpenAI provides multiple ways to manage conversation state across turns:

| Method | API | Description |
|--------|-----|-------------|
| **Manual state management** | Both | Replay previous messages/Items as input on each turn |
| **`previous_response_id`** | Responses | Chain stored responses; OpenAI manages prior context |
| **Conversations API** | Responses | Persistent conversation object with durable ID |
| **Encrypted reasoning** | Responses | Stateless + reasoning preserved via encrypted tokens |

### Method 1: Manual State Management

Provide previous messages/Items as input on each request. For reasoning models in stateless mode, add `reasoning.encrypted_content` to `include` and preserve every Item in `response.output`.

**Chat Completions:** Append `response.choices[0].message` to `messages` array, then add next user message.

**Responses API:** Append `response.output` (all Items) to `input` array, then add next user message.

```python
history = [{"role": "user", "content": "tell me a joke"}]

response = client.responses.create(
    model="gpt-5.6",
    input=history,
    store=False,
    include=["reasoning.encrypted_content"],
)

history += response.output  # preserve all Items including encrypted reasoning
history.append({"role": "user", "content": "tell me another"})

second_response = client.responses.create(
    model="gpt-5.6",
    input=history,
    store=False,
    include=["reasoning.encrypted_content"],
)
```

### Method 2: `previous_response_id` (Responses API)

Chain responses by referencing the previous response ID. Requires `store: true`.

```python
response = client.responses.create(
    model="gpt-5.6",
    input="tell me a joke",
    store=True,
)

second_response = client.responses.create(
    model="gpt-5.6",
    previous_response_id=response.id,
    input=[{"role": "user", "content": "explain why this is funny."}],
    store=True,
)
```

**Important notes:**
- `previous_response_id` does **not** carry over the previous response's top-level `instructions` — resend stable instructions on each request.
- Even when using `previous_response_id`, all previous input tokens for responses in the chain are **billed as input tokens**.
- In WebSocket mode, continuation uses the same `previous_response_id` semantics but over a persistent socket with repeated `response.create` events. The connection-local cache keeps the most recent previous response in memory for low-latency continuation.

### Method 3: Conversations API

The Conversations API (`/v1/conversations`) works with the Responses API to persist conversation state as a long-running object with its own durable identifier. After creating a conversation, you can keep using it across sessions, devices, or jobs.

```python
# Create a conversation
conversation = openai.conversations.create()

# Use it in responses
response = openai.responses.create(
    model="gpt-5.6",
    input=[{"role": "user", "content": "What are the 5 Ds of dodgeball?"}],
    conversation="conv_..."
)
```

**Conversations store Items**: messages, tool calls, tool outputs, and other data.

**Data retention:**
- Response objects are saved for 30 days by default (viewable in dashboard logs or retrievable via API).
- Conversation objects and their items are **not** subject to the 30-day TTL. Any response attached to a conversation has its items persisted with no 30-day TTL.
- Disable response storage with `store: false`.

### Method 4: Encrypted Reasoning (Stateless + Reasoning)

See §5. Set `store: false` + `include: ["reasoning.encrypted_content"]`. The API returns encrypted reasoning tokens that can be passed back in future requests. For ZDR organizations, `store: false` is enforced automatically.

### Context Window Management

The **context window** is the maximum tokens (input + output + reasoning) per request. Token types counted:

- **Input tokens** — inputs in `messages`/`input` array
- **Output tokens** — tokens generated in response
- **Reasoning tokens** — used by reasoning models to plan (counted toward context window)

Tokens generated in excess of the context window may be truncated.

### Compaction

For managing large contexts:

- **Server-side compaction**: `/responses` with `context_management` and `compact_threshold`.
- **Standalone compact endpoint**: `/responses/compact` for explicit compaction control.

### `phase` Field Note

When troubleshooting cases where GPT-5.5 treats an intermediate update as the final answer, verify your integration preserves the assistant message `phase` field correctly.

## 12. File Inputs

### Main Concepts

OpenAI models can accept files as `input_file` items. In the Responses API, files can be sent as Base64-encoded data, a file ID from the Files API (`/v1/files`), or an external URL.

### File Processing by Type

| File Type | Processing |
|-----------|-----------|
| **PDF files** | On vision-capable models (`gpt-4o`+): extracts both text AND page images, sends both to model |
| **Non-PDF documents/text** (`.docx`, `.pptx`, `.txt`, code files) | Extracts text only |
| **Spreadsheets** (`.xlsx`, `.csv`, `.tsv`) | Spreadsheet-specific augmentation flow (see below) |

### Spreadsheet Augmentation

For spreadsheet-like files (`.xlsx`, `.xls`, `.csv`, `.tsv`, `.iif`): the API parses up to the first **1,000 rows per sheet** and adds model-generated summary and header metadata so the model works from a smaller, structured view.

### PDF Detail Levels (Responses API only)

| `detail` value | Behavior |
|----------------|----------|
| `auto` (default) | Uses `high` for GPT-5.6+; `low` for earlier models |
| `low` | Fewer input tokens |
| `high` | More visual detail (dense charts, small print, diagrams) |

The `detail` setting only affects PDF page image processing. Extracted text is always included. Chat Completions does not support `detail`.

### Non-PDF Image/Chart Limitations

For non-PDF files, the API does **not** extract embedded images or charts into model context. To preserve chart/diagram fidelity, convert the file to PDF first, then send the PDF.

### API Parameters

#### Responses API — `input_file` content item

| Field | Description |
|-------|-------------|
| `type` | `"input_file"` |
| `filename` | File name (for Base64) |
| `file_data` | Base64-encoded data URI: `data:application/pdf;base64,...` |
| `file_id` | File ID from Files API (`file-...`) |
| `file_url` | External URL to the file |
| `detail` | PDF detail level: `"auto"` / `"low"` / `"high"` |

#### Chat Completions API — `file` content item

| Field | Description |
|-------|-------------|
| `type` | `"file"` |
| `file.file_id` | File ID from Files API |
| `file.file_data` | Base64-encoded data URI (with `file.filename`) |

**Note:** Chat Completions does **not** support file URLs or `detail`.

### File Delivery Methods

| Method | Responses API | Chat Completions |
|--------|--------------|-----------------|
| Base64-encoded data | Yes (`file_data`) | Yes (`file.file_data`) |
| Files API file ID | Yes (`file_id`) | Yes (`file.file_id`) |
| External URL | Yes (`file_url`) | **No** |

### Files API — Uploading

```python
file = client.files.create(
    file=open("document.pdf", "rb"),
    purpose="user_data"
)
# Then reference file.id in the response request
```

Upload purpose should be `user_data` for files intended as model inputs.

### File Size Limits

- Each individual file: under **50 MB**.
- Combined total across all files in a single request: also capped at **50 MB**.

### Accepted File Types

| Category | Common Extensions |
|----------|-------------------|
| **PDF files** | `.pdf` |
| **Spreadsheets (Excel)** | `.xls`, `.xlsx`, `.xla`, `.xlb`, `.xlc`, `.xlm`, `.xlt`, `.xlw` |
| **Spreadsheets (CSV/TSV/IIF/Google Sheets)** | `.csv`, `.tsv`, `.iif` |
| **Rich documents** | `.doc`, `.docx`, `.dot`, `.odt`, `.rtf` |
| **Presentations** | `.ppt`, `.pptx`, `.pot`, `.ppa`, `.pps`, `.pwz`, `.wiz` |
| **Text and code** | `.txt`, `.md`, `.json`, `.html`, `.xml`, `.js`, `.mjs`, `.py`, `.c`, `.cpp`, `.css`, `.sql`, `.log`, `.eml`, `.ics`, `.vcf`, `.vtt`, `.srt`, `.rst`, `.bat`, `.pl`, `.ksh`, `.conf`, `.in`, `.def`, `.dic`, `.list`, `.nws`, `.mht`, `.mhtml`, `.mime`, `.markdown`, `.cxx`, `.hh`, `.cc`, `.h`, `.asm`, `.s` and many more |

Also supported: Apple Pages, Google Docs, Apple Keynote, Google Slides, Google Sheets formats.

### Related Tools (When File Inputs Aren't Ideal)

| Need | Better Tool |
|------|-------------|
| Retrieval over large files | [File Search](/api/docs/guides/tools-file-search) |
| Spreadsheet-heavy analysis (aggregations, joins, charting, custom calculations) | [Hosted Shell](/api/docs/guides/tools-shell) |

## 13. Streaming

### Main Concepts

Both APIs support streaming to surface generation progress incrementally.

### Chat Completions Streaming

Set `stream: true`. Returns incremental chunks with a `delta` field:
- Text: `delta.content`
- Tool calls: `delta.tool_calls`

### Responses API Streaming

Set `stream: true`. Returns **typed server-sent events** — consumers must branch on each event's `type`:

| Event Type | Description |
|------------|-------------|
| `response.created` | Response object created |
| `response.output_text.delta` | Text output delta |
| `response.completed` | Response completed |
| `response.function_call_arguments.delta` | Function call arguments delta |
| `response.function_call_arguments.done` | Function call arguments complete |
| `error` | Error event |

**Migration note:** Do not reuse Chat Completions streaming chunk handlers without handling typed Responses events.

## 14. Context Window & Compaction

### Context Window

The maximum tokens (input + output + reasoning) per request. Varies by model.

### Token Counting

Use the [tokenizer tool](https://platform.openai.com/tokenizer) (built with the [tiktoken library](https://github.com/openai/tiktoken)) to estimate token counts. API endpoints for counting tokens are also available (see token-counting guide).

### Compaction

For long conversations approaching the context window limit:

- **Server-side compaction**: Configure `context_management` with `compact_threshold` on `/responses` requests. The API automatically compacts context when the threshold is reached.
- **Standalone compact endpoint**: `POST /responses/compact` for explicit control over compaction.

### Prompt Caching

The Responses API benefits from improved cache utilization (40–80% improvement vs Chat Completions in internal tests). Use `tool_choice: {"type": "allowed_tools", ...}` to restrict tools without modifying the tools list, preserving cache savings.

| Grouped tools by domain | Namespaces (`type: "namespace"`) |

### Structured Output Decision Matrix

| Need | Recommended Approach |
|------|---------------------|
| Structure the model's response to the user | `text.format` (Responses) / `response_format` (Chat Completions) with `json_schema` + `strict: true` |
